# 企业主要联系人驾驶证留存设计

> 状态：产品负责人于 2026-08-14 确认采用“沿用现有驾驶证证据流程，但明确证件属于企业主要联系人”。
>
> 本文修订 `2026-08-13-in-person-customer-onboarding-design.md` 中“企业跳过驾驶证 KYC”的旧规则。
> 冲突时以本文为准。本文不改变“企业只有一个主要联系人”和“当前纯 Mock、不接真实 AI”的既有边界。
>
> 非阻断原则：驾驶证是应留存的联系人资料，但缺失或未核验时只形成提醒和待补状态，不阻止企业建档。
> 业务操作优先遵循 `../decisions/2026-08-14-record-remind-never-block-business.md`。

## 1. 决定与目标

企业是客户档案主体，但企业本身不是驾驶证主体。企业建档时，为唯一主要联系人提供本人驾驶证留存与现场核对流程；未提供或未完成核对时仍可建档，系统记录待补／待核验。

固定业务顺序为：

```text
主要号码唯一性检查（号码可留空）
  → 已填写号码可做 OTP 验证
  → 上传或拍摄主要联系人驾驶证正面
  → AI 辅助提取或人工填写姓名、出生日期、性别、证件地址
  → 员工确认联系人本人、原件和四项资料一致
  → 填写企业名称、联系人职位、企业地址等正式资料
  → 按当前事实一次性创建企业档案、已有验证记录、缺口提醒和审计
```

OTP 或主要联系人驾驶证核对未完成时，允许创建企业客户；系统如实标记“OTP 待验证”“主要联系人驾驶证待补／待核验”，并进入提醒和后续补录。AI 辅助失败时保留人工填写路径。

## 2. 数据归属

### 2.1 企业正式资料保持不变

下列资料继续属于企业档案：

- 企业名称；
- 企业通讯地址；
- 主要号码、备用号码、WhatsApp、Email；
- 客户状态、语言、TRN、联系渠道；
- 主要联系人职位／关系。

现有通用姓名字段继续表示唯一主要联系人的正式姓名。企业通讯地址继续使用现有企业地址字段，不得被驾驶证地址覆盖。

### 2.2 驾驶证证据明确主体

沿用 `verificationArchive.kycRecords`，不新增联系人表或多联系人系统。企业主要联系人新写入的驾驶证记录必须是 scoped record，并包含：

```text
subjectType: organization_primary_contact
subjectProfile:
  name
  birthDate
  sex
  address
```

`subjectProfile.address` 是驾驶证上的联系人地址，不是企业通讯地址。四项均为员工确认时的快照，只允许姓名、出生日期、性别和地址；不得加入 TRN、驾驶证号码、类别、签发／到期日、签发地点、签名、头像特征、全文或原始 AI 响应。

现有未带 subject 的个人 KYC 记录继续按旧个人记录读取。现有企业记录若没有明确的 `organization_primary_contact` 主体，不得自动认定为当前主要联系人的有效驾驶证。

## 3. 新建企业流程

### 3.1 页面与状态

- 企业不论手机号是否填写或 OTP 是否完成，都可进入现有驾驶证上传、预览、旋转、裁剪、AI 辅助和人工填写界面；
- 文案使用“主要联系人驾驶证”，不得写成“企业驾驶证”；
- 四项字段为主要联系人姓名、出生日期、性别、证件地址；
- 企业名称、联系人职位、企业地址继续在企业正式资料区域填写；
- 主要联系人姓名以已确认驾驶证姓名为来源，并继续经过现有安全音译确认；
- 手机号、客户类型、图片、旋转、裁剪或四项变化时，继续沿用现有 attempt、KYC、姓名确认和最终预览失效规则；
- 当前 Mock 仅在显式点击“AI辅助识别”后返回清楚标注的模拟结果；默认未接服务时失败关闭并保留人工填写。

现有 reducer、图片编辑器、证据准备、AI 接口边界和会话隔离规则继续复用，不建立第二套企业证件流程。

### 3.2 Store 记录与校验

企业 onboarding session 支持 `kyc_submitted` 和 `kyc_confirmed`。preview/create 在证据已提供时校验其真实性和归属；证据缺失时写入 gap 和提醒，不拒绝建档：

1. 保存 OTP 当前状态；未验证则生成提醒；
2. 驾驶证已提供时，证据必须可读取且未被其他记录占用；未提供则生成待补；
3. KYC 已确认时记录当前 actor；未确认则生成待核验；
4. 已写入企业驾驶证记录的 subject 必须是 `organization_primary_contact`；
5. 驾驶证姓名与最终主要联系人姓名不一致时显示提醒并要求后续核对，但允许员工继续；
6. 企业地址与 `subjectProfile.address` 分别持久化；
7. preview、sourceRevision、duplicate candidate 和 `clientMutationId` 继续提供一致性、提醒和幂等保护，不充当业务审批门槛。

最终创建仍只调用一次 `persist()`。成功后同时写入企业客户、实际已有的 OTP／联系人驾驶证记录、缺口提醒、compact audit 和创建回执；失败或响应丢失继续使用同一 preview token 与 mutation ID 安全重试，避免一次点击被技术性重复执行。

## 4. 已有企业客户

- 没有当前有效 scoped record 的企业显示“主要联系人驾驶证：待补”，并计入验证待补数量；
- 详情页提供“补充主要联系人驾驶证”或“重新核验”操作，复用现有证据上传、四项填写和现场确认界面；
- 最新有效记录的驾驶证姓名必须与当前主要联系人姓名来源一致；不一致时状态为待重新核验；
- 更换或修改主要联系人姓名不会删除旧证据，但旧记录不得继续证明新联系人；
- 补录时若驾驶证姓名与当前主要联系人不一致，显示明确提醒；员工可先保存证据为待核对，再通过现有姓名修改或重新核验流程处理；
- 历史无 subject 的企业 KYC 记录可以保留在审计／历史证据中，但不得自动算作当前联系人已核验；
- 不自动伪造或回填历史证据、核验人、核验时间或审计事件。

企业详情的企业名称、企业地址和主要联系人职位继续读取企业正式资料；主要联系人出生日期、性别和证件地址只从当前有效 scoped KYC 快照显示，并明确标注为证件资料。

## 5. 审计、权限与隐私

- 沿用当前 KYC submit/verify 权限、access-first 校验、actor 绑定、session 失效和审计留痕；
- 审计文案和 compact changes 必须写“主要联系人驾驶证”，不能写“企业驾驶证”；
- 调取证据继续先通过 `validateEvidenceAsset`，不得在 DOM、URL、console 或审计中重复输出 Base64；
- 原始图片、裁剪工作图、AI 原文、confidence、坐标、模板名、供应商请求 ID 和供应商响应不得持久化；
- 浏览器仍不得直接连接外部 AI、持有供应商密钥或引入供应商 SDK；
- 当前证据存储仍是 Mock 演示，界面继续显示“请勿上传真实客户证件”。

## 6. 兼容与迁移

本轮不新增完整 `primaryContact` 子实体，不支持多个联系人，也不把联系人驾驶证字段塞入企业通讯地址。

KYC record 在现有 schema v3 内扩展为严格兼容 union：旧记录保持原 exact key 形状，新企业联系人记录必须使用另一组 exact keys，并带 scoped subject 和四项快照。validator 按具体分支严格检查 own keys、四项值、时间顺序、证据大小和 ID 唯一性；不得以额外可选键或宽松 validator 兼容。本轮不提升 schema 版本，也不改写任何既有持久化记录。

旧企业客户不会在读取或迁移时自动生成联系人驾驶证。其状态只会如实显示“待补”。

## 7. 验收标准

### 7.1 新建企业

- 页面按号码查重、OTP、主要联系人驾驶证、现场确认、正式资料的顺序引导，但允许员工在任一业务缺项下继续建档；
- 未上传驾驶证、未填完四项或未勾选现场确认时，预览显示缺项摘要，创建后保存对应待补／待核验提醒；
- AI 辅助与人工填写共用同一证据和确认规则；
- 创建结果按事实包含已验证记录或缺口；如驾驶证已核验，则记录必须是 scoped 的主要联系人驾驶证；
- 联系人证件地址和企业地址分别保存、分别显示；
- 430 px 下保持单列、无根横向溢出，固定操作区可用。

### 7.2 已有企业

- 现有企业默认显示主要联系人驾驶证待补，不再显示“不适用”；
- 补录后可查看证据和四项快照，刷新后状态保持；
- 更换联系人姓名后旧证据保留历史但当前状态变为待重新核验；
- 无 subject 的旧企业记录不能自动通过；
- 个人客户现有 KYC、OTP、协议、风险、备注、车辆关系和审计行为不回退。

### 7.3 自动验证

- store/API 单元测试覆盖企业 KYC submit/verify、缺资料仍可 preview/create、主体绑定、地址分离、提醒、幂等、失败零写和历史兼容；
- reducer/E2E 覆盖企业 AI 辅助、人工回退、证据失效、会话切换、430 px、已有企业补录及联系人更换失效；
- 隐私测试继续证明只持久化获准四项和压缩证据；
- 最终通过 typecheck、collaboration、全量 unit、build、全量 E2E、diff check，以及桌面／430 px 原图验收。

## 8. 本轮不做

- 多联系人、联系人列表或联系人历史任职模型；
- 驾驶证号码、TRN、类别、签发／到期日等额外提取；
- 真实短信、真实后端、数据库、对象存储或真实 AI 服务接入；
- 自动把企业旧 KYC 猜成当前联系人证据；
- 因本次驾驶证要求改写企业地址、OTP、协议或其他既有业务语义。
