# 客户与车辆业务模型设计

## 目标

为客户与车辆工作区提供可持久化的 Mock 业务模型、权限边界、保存流程和稳定 API，并让已接入的列表、详情与编辑表单保持同一业务口径。

## 已确认业务口径

- 客户是正式业务主体，不设置散客；客户至少提供手机号、WhatsApp 或 Email 之一。
- 客户重复只提示，不自动合并；保存人必须显式确认继续建立重复候选。
- 非空车牌唯一；重复车牌必须返回已有车辆，不能产生第二份车辆档案。
- 车辆与客户关系用带起止时间的数组保存，结束关系不会删除历史。
- 每辆车最多只能有一个 `endedAt = null` 的当前客户；允许车辆暂时没有当前客户。
- 换绑客户时，系统在同一次原子保存中结束旧的当前关系并建立新的当前关系。旧关系、旧工单、费用、照片和收付款归属保持原样，不回写历史客户。
- 清除当前客户时只结束现有关系，不创建新关系。历史关系的客户、开始时间和既有结束时间不可删除或改写。
- 第一版不增加车主、司机、付款人等关系角色；“当前客户”是唯一的当前绑定主体。
- 客户停用和关系结束保留全部历史；所有写入记录操作者、时间、前后值与原因。
- Mock 保存采用乐观并发 revision；持久化失败必须保持原子，不能出现页面报错但数据已改变。

## 既有 Mock 数据迁移

- 持久化结构升级到新 schema；新状态在读取和保存边界都校验“每辆车最多一个当前客户”。
- 旧 schema 若存在多个当前关系，迁移时保留 `startedAt` 最新的一条；时间相同则保留关系 ID 排序最后的一条，其他关系结束于保留关系的开始时间。
- 迁移只调整冲突关系的 `endedAt`，不得丢弃客户、车辆、业务聚合、审计或其他历史关系。
- 固定演示种子改为一辆车一个当前客户，并保留之前客户的结束记录，便于页面同时展示当前客户和历史客户。

## 权限

- `superadmin`、`frontdesk_admin`：可读完整目录，可新建和编辑。
- 其他身份：完整目录 API 暂时拒绝。后续若开放收银、配件或维修工，必须使用受限 DTO，不能从完整响应中临时隐藏字段。
- 无会话返回 403；损坏会话返回 401；权限在读取种子或构造响应前执行。

## 数据与 API

- `GET /api/customer-vehicles`：汇总、客户列表、车辆列表。
- `GET /api/customers/:id`、`GET /api/vehicles/:id`：原地详情所需完整记录。
- `POST /api/customers/preview`：规范化输入、返回重复候选与绑定 revision 的预览凭证。
- `POST /api/customers`：必须提交预览凭证；存在候选时必须显式 `confirmPossibleDuplicate`。
- `PATCH /api/customers/:id`：提交 `expectedRevision`，更新后写审计。
- `POST /api/vehicles/preview`：返回同车牌已有车辆，非空车牌重复时不可保存。
- `POST /api/vehicles`、`PATCH /api/vehicles/:id`：保存车辆、唯一当前客户关系和历史，使用预览/并发保护；绕过 UI 提交多个当前客户必须在 domain 层拒绝。

## 页面交互

- 车辆表单将“客户关系（可多选）”改为单选的“当前客户”，并提供“暂无当前客户”。
- 编辑时选中已有当前客户；选择另一客户即表示换绑。保存预览明确展示旧客户结束、新客户开始的结果。
- 车辆列表和详情只显示一个当前客户；历史客户仍按起止时间完整展示。
- 汇总卡不再描述“允许多位当前客户”，改为说明“一车一位当前客户”。

## 第一版不处理

- 不实现真实 OCR、真实附件上传、短信、WhatsApp、客户合并或删除审批。
- 不新增多人角色体系、公司账户层级或财务内账。
- 不改全局抬头、侧栏、主题、现有 revenue/performance 文件。

## 验收

- 种子数据关系完整、汇总与列表一致。
- 未授权读取不返回任何姓名、电话、VIN、风险或金额。
- 客户重复提示、车牌唯一、revision 冲突、持久化失败与重试均有真实行为测试。
- 创建、换绑、清除当前客户均保证每辆车最多一个当前关系；历史不可变并写入 before/after 审计。
- 旧多当前关系 Mock 状态可确定迁移，迁移后客户、车辆和历史记录不丢失。
- 车辆表单只能选择一个当前客户；列表、详情和汇总不再出现多当前客户文案或并列当前客户。
- WorkBuddy 接入后在独立端口完成桌面、430px、深色、键盘与无 console/page error 验收。
