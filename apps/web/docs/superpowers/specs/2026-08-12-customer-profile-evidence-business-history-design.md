# 客户档案真实性、验证证据与业务历史一致性设计

> 状态：产品负责人已于 2026-08-12 批准推荐方案及“纯 Mock 安全音译”方案。本文补充并细化 `2026-08-10-orders-documents-billing-archives-design.md` 的客户／车辆档案要求；两份规格冲突时，以本文对客户资料、验证证据、返回导航和客户业务聚合的规定为准。

> 2026-08-13 驾驶证样本修订：产品负责人提供真实牙买加驾驶证作为字段位置参考，并明确驾驶证只提取“姓名、出生日期、性别、地址”四项。真实样本及其中个人资料不得复制进仓库、种子或测试；TRN、驾照类别、号码、签发／到期日、签发地点和签名等均不进入提取结果。

## 1. 目标

本轮不是隐藏几个难看的字段，而是纠正客户档案中的五类事实错误：

1. 中文名与英文名必须是同一姓名的对应音译，不得把两个不同姓名并排显示；
2. 正式资料只保留有业务意义、可维护或可追溯的资料；
3. OTP、KYC、客户服务协议必须保存并能调取支持其状态的证据；
4. 从客户进入车辆后必须能明确返回原客户；
5. 累计消费、付款摘要和业务记录必须由同一组 BO／Invoice／Payment 数据计算。

系统继续严格采用纯 Mock 路线：不接真实短信、OCR、对象存储、翻译服务或数据库，但界面、接口形态、验证约束、持久化和错误流程必须完整可演示。

## 2. 已确认的现状问题

- `CUST-UAT-001` 同时显示 `黄艾丽 / Alicia Bennett`，两者不是音译关系；邮箱和配偶姓氏又支持 Bennett 身份。
- 现有姓名 fallback 会把未知英文全名缩成一个中文姓氏，例如 `Jason Wong → 王`，产生不完整姓名。
- 正式资料展示来源、近期业务、近期业务时间、进行中业务和风险说明；这些字段与真实业务档案重复或没有闭环。
- 个人客户出现无法新增、编辑或删除的额外联系人；企业客户的额外联系人又与已有“主要联系人”重复。
- `loyal`、`morning-pickup` 等自由英文标签没有中文解释、筛选、自动动作或独立维护入口。
- OTP 只保存布尔值和时间，不保存验证号码；已验证后没有“联系不上／重新验证”入口。
- KYC 点击即通过，不要求证件；客户详情无法查看驾驶证，现有 Alicia 样本还是车辆登记证而非驾驶证。
- 协议界面声称是电子协议，却不保存纸／电类型、签名图、签署文件或纸质档案位置。
- 附件记录只有文件名，没有可访问资源，无法查看或下载。
- 客户进入车辆详情后，顶部只会返回车辆列表，来源客户丢失。
- Alicia 的 JMD 532,000、14 单等数字来自客户静态摘要，业务记录来自另一套独立演示数据，所以会出现“累计消费很高但 BO 为空”。

## 3. 产品不变量

以下规则必须同时由类型、Mock API、持久化迁移、页面和测试约束：

1. 没有证据，不得显示“已验证／已核验／已签署”。
2. 没有实际 Invoice，不得显示累计消费；没有实际 Payment，不得显示已付金额。
3. 客户、车辆、BO、Invoice 和 Payment 只通过稳定 ID 关联，不通过姓名或电话号码猜测关联。
4. 用户录入的正式资料必须能从客户详情进入编辑；系统派生和历史记录可以只读，但必须能追溯到来源记录。
5. 没有维护入口、业务消费者或审计价值的字段不进入页面，也不继续作为新数据模型的一部分。
6. 历史证据不可覆盖。重新 OTP、重新 KYC、重签协议都新增记录并保留旧记录。
7. Mock 流程可以使用固定验证码和合成证件，但不得用不相干文件冒充证据。

## 4. 客户姓名与纯 Mock 安全音译

### 4.1 单一录入框

个人客户创建和编辑只显示一个主输入框“客户姓名”。系统按字符判断原名方向：

- 包含中文字符：原名是中文；
- 仅包含拉丁字符：原名是英文；
- 混合脚本、数字姓名或空白输入：拒绝保存并给出明确校验提示。

输入框下方显示只读的“对应音译”，它是确认结果，不是第二个姓名输入框。用户通过独立的“确认音译”按钮确认该只读结果；原名继续输入后，旧确认立即失效。预览未生成或未确认时不能保存。

保存后记录以下事实：

```text
nameSourceScript       zh | en
nameSourceValue        用户输入的原名
nameZh                 中文姓名
nameEn                 英文／拼音姓名
transliterationMethod  offline_pinyin | exact_name_dictionary
transliterationVersion 音译规则版本
```

客户列表和详情可以同时显示 `nameZh / nameEn`，但两侧必须来自同一次音译结果。

### 4.2 中文输入

中文姓名使用离线汉语拼音，不调用网络：

- 姓在前、名在后；
- 姓与名之间一个空格，名内部不拆成多个单字空格；
- 去声调，首字母大写；
- 常见复姓按复姓处理；
- 示例：`陈志远 → Chen Zhiyuan`、`黄艾丽 → Huang Aili`。

如果离线拼音器不能完整处理所有字符，显示“无法安全音译”，阻止保存；不得保留旧英文别名或自行拼凑。

### 4.3 英文输入

英文姓名采用已批准的纯 Mock 安全方案：只做“完整姓名词典”精确匹配，不做姓氏单字 fallback，也不使用通用猜音算法。

- 词典覆盖所有 UAT、批量演示和单元测试中允许创建的英文姓名；中文演示姓名生成的拼音对也写入同一版本的反向完整姓名词典，保证 round-trip；
- 匹配忽略首尾空白和大小写，但输出使用词典的规范拼写；
- 示例：`Alicia Bennett → 艾丽西亚·贝内特`；
- 未命中时显示“当前纯 Mock 音译库没有该完整姓名”，阻止保存；
- 不允许出现 `Jason Wong → 王`、`Alice Chin → 蔡` 这类只有姓氏的结果。

真实后端接手后可在同一接口后替换为经人工确认的音译服务；本轮不接真实翻译 API。

### 4.4 现有客户校正与迁移

- 所有已成对的中文演示客户以中文原名为准，英文侧统一重算为拼音，不再保留 `Vincent Chang` 等与中文名不对应的英文别名。
- `Alicia Bennett` 的身份由英文名、邮箱和家庭资料共同支持，因此以英文为原名，中文改为 `艾丽西亚·贝内特`，不得改成 Alicia Wong。
- 已有记录只有英文且完整姓名能命中词典时补中文音译；不能命中时保留单语原名并标记 `needs_transliteration_review`，不得猜一个错误中文名。
- 已有任意双语 tuple 必须通过同一规则往返校验；不一致的数据不能继续标记为已完成资料。
- 迁移保存原始 tuple 到审计记录，便于追查旧值，不静默抹掉历史。

### 4.5 企业客户

企业客户继续使用一个“企业名称”字段，不把企业名当个人姓名音译。企业仅保留一个可编辑的“主要联系人”；主要联系人姓名始终沿用个人姓名的单输入框和安全音译规则。

## 5. 正式资料与可维护边界

### 5.1 个人客户正式资料

正式资料合并为一个可编辑区，包含：

- 客户姓名及对应音译；
- 称谓、性别、出生日期、TRN、语言；
- 主要电话、备用电话、WhatsApp、Email、首选联系渠道；
- 地址、客户状态、登记时间。

登记时间是系统审计事实，只读显示；其余用户录入资料从同一区域进入编辑。驾驶证照片属于 KYC 证据，不再藏在普通编辑表单里。

### 5.2 企业客户正式资料

企业客户包含：

- 企业名称；
- 一个主要联系人姓名；
- 主要联系人的职位／关系；
- 电话、备用电话、WhatsApp、Email、首选联系渠道；
- 企业地址、客户状态、登记时间。

本轮不实现多联系人列表。现有重复 `contacts[]` 数据删除；以后确认需要多个部门联系人时，必须作为具备新增、编辑、删除和“设为主要联系人”能力的完整功能另行设计。

### 5.3 删除的无闭环字段

从页面、创建／编辑表单、新种子、公开类型和持久化新模型中删除：

- `source`；
- `recentBusiness`；
- `recentBusinessDate`；
- `activeBusinessCount`；
- `tags`；
- `contacts[]`；
- `riskNote`；
- 可手工编辑的 `riskLevel`；
- 客户静态 `orders[]`；
- 客户静态 `paymentSummary`。

风险继续使用现有 `riskFlags` 闭环。页面风险等级由当前有效风险条目派生，普通资料编辑不能绕过风险条目直接改等级。

### 5.4 其他页面信息

- 客户备注保留，因为已有明确的新增／编辑记录能力。
- 变更历史、验证历史和财务历史是不可篡改事实，不要求直接编辑，但必须显示操作者、时间和来源。
- 没有实际跳转、查看或下载入口的附件不显示；缺少真实 Mock 资源的旧附件迁移为“证据待补”或删除无意义种子。
- 没有完成动作的示例任务、沟通或状态块不得继续作为正式事实展示。

## 6. 验证证据模型

### 6.1 通用证据资源

可调取文件统一使用：

```text
EvidenceAsset
  id
  fileName
  url
  mimeType
  sizeBytes
  createdAt
  createdBy
```

`url` 必须在刷新后仍可打开。种子资源使用仓库中的合成文件；运行时 Mock 上传压缩到每个资源不超过 512 KiB，并以允许的 `data:` URL 持久化，不使用刷新即失效的临时 Blob URL。KYC 接受 JPEG／PNG，协议扫描件接受 JPEG／PNG／PDF；超出大小或类型不符时在选择文件后立即报错。

### 6.2 OTP 记录

每次 OTP 保存独立记录：

```text
OtpVerificationRecord
  id
  phoneE164
  requestedAt
  verifiedAt?
  verifiedBy?
  invalidatedAt?
  invalidatedBy?
  invalidationReason?
```

当前 OTP 状态由记录历史派生，不再单独相信布尔值。状态固定为 `unverified | pending | verified | needs_reverification | evidence_missing`。

纯 Mock 流程：

1. 对话框显示准备验证的完整电话号码；
2. 无有效主要电话时禁止发送，并引导先编辑正式资料；
3. 点击发送后进入验证码输入状态；
4. 输入固定 Mock 验证码 `123456` 后才成功，演示界面明确标注该验证码；
5. 成功记录号码、操作人和时间；
6. 已验证卡仍保留“标记联系不上”和“重新 OTP”操作；
7. 标记联系不上必须填写原因，旧记录作废但不删除；
8. 新号码验证成功后更新主要电话，并新增验证记录；
9. 如果主要电话后来被普通编辑改动，当前状态自动变为“号码已变更，需重新验证”。

OTP 卡始终显示当前已验证号码和时间，历史抽屉显示所有验证与作废记录。

### 6.3 驾驶证 KYC

KYC 记录至少包含：

```text
KycVerificationRecord
  id
  documentType = drivers_license
  frontAsset
  backAsset?
  submittedAt
  verifiedAt?
  verifiedBy?
  invalidatedAt?
  invalidationReason?
```

KYC 当前状态固定为 `pending | verified | needs_reverification | evidence_missing`，由最新有效记录及其证据派生。

要求：

- 正面驾驶证照片是核验前置条件，背面可选；
- KYC 卡直接提供“查看驾驶证”入口，无需进入编辑客户；
- 查看器显示同一份持久化证据，可放大、关闭和重新打开；
- 无照片的 Mock API 请求返回校验错误，不能一键变成已核验；
- Alicia 的车辆登记证样本删除，替换为带明显“合成演示资料”水印的虚构驾驶证；
- 重新 KYC 新增记录并保留旧证据历史。

驾驶证的结构化资料范围固定为四项：

```text
姓名
出生日期
性别
地址
```

- 完整驾驶证图片继续作为可调取的 KYC 证据保存；结构化提取不复制 TRN、驾照类别、驾照号码、签发／到期日、签发地点、签名或其他字段；
- 提取结果先进入可编辑确认预览，用户确认后才合并到客户正式资料，不得静默覆盖已有资料；
- 驾驶证姓名仍走唯一姓名框及安全音译确认，不能绕过姓名 receipt 或把英文／中文两侧分别手改；
- 出生日期规范为 `YYYY-MM-DD`，性别和多行地址转换为可编辑的正式资料值；
- 本轮仍不接真实 OCR 服务。内置合成驾驶证可以使用确定性 Mock 提取 fixture；任意新上传图片若没有可信提取结果，只显示这四个待核对字段并要求人工填写，不得伪称自动识别成功；
- 产品负责人提供的真实驾驶证只作版式和字段位置参考，不作为资源、fixture、截图或快照提交。

### 6.4 客户服务协议

每次签署保存独立记录：

```text
AgreementRecord
  id
  version
  medium = electronic | paper
  signedAt
  signedBy
  recordedBy
  signedDocumentAsset?
  signatureAsset?
  paperScanAsset?
  physicalRecordNumber?
  physicalStorageLocation?
```

协议当前状态固定为 `pending | signed | expired | evidence_missing`，由最新适用版本及其证据派生。

电子版要求：

- 保存签名板生成的 PNG 签名证据，并生成可重新打开、下载的签署版 PDF；
- 详情显示“电子版”、版本、签署人、时间和“查看签署文件”。

纸质版要求：

- 必须上传扫描件，或同时填写实体档案编号和存放位置；
- 详情显示“纸质版”以及“查看扫描件”或明确档案位置；
- 不能只点一次按钮就显示已签署。

协议过期或重签时保留旧版本历史。页面标题不得在没有类型事实时硬编码“电子协议”。

### 6.5 旧验证数据

- 新的客户 Mock schema 升级版本并提供显式迁移。
- 对浏览器中只有旧布尔状态、时间和版本、但没有号码／文件／签名证据的记录，保留旧时间作为历史线索，当前状态改为“证据待补”。
- 固定 UAT 种子可以随代码提供完整合成证据，因此其状态可保持已完成。
- 迁移不得根据当前电话猜测旧 OTP 当时验证的号码，也不得根据文件名捏造不存在的附件。
- 所有验证、作废和重签动作进入客户详情可见的统一审计历史。

## 7. 客户、车辆、BO 与 Invoice 的单一事实链

### 7.1 稳定 ID

客户档案和订单域必须共享同一客户 ID、车辆 ID。禁止继续使用姓名、中文名或电话号码做模糊匹配。`LinkedOperationsState.customers` 中每个客户 ID 都必须存在于客户存储，`LinkedOperationsState.vehicles` 中每个车辆 ID 都必须存在于车辆存储；引用不成立时，状态校验直接拒绝该数据。

```text
Customer.id ── VehicleRelationship.customerId
            └─ BusinessOrder.customerId

Vehicle.id  ── BusinessOrder.vehicleId

BusinessOrder.id ── Invoice.businessOrderId
Invoice.id       ── Payment.invoiceId
                 └─ Refund.invoiceId
```

订单域可以保留客户／车辆显示快照，但关联权威始终是 ID。客户和订单种子改为读取同一份 canonical identity fixture；删除订单种子的 `independent_demo` 身份，不再维护第二套互不相认的客户／车辆目录。

### 7.2 统一派生器

建立一个无副作用的客户业务档案派生器，输入 `LinkedOperationsState` 和 `customerId`，输出：

- 该客户全部 BO；
- BO 对应车辆；
- 每个 BO 的全部 Invoice；
- 每张 Invoice 的最新版本；
- Payment、Refund、净已付和余额；
- BO 数、Invoice 数、累计开票、净已付、未付；
- 可直接渲染的业务历史行。

客户英雄区、付款摘要、业务记录数量和业务记录列表必须消费同一个派生结果，不允许各自重新匹配。

### 7.3 金额口径

- 累计消费：该客户全部已存在 Invoice 的最新版本 `totalJmd` 之和；
- 已付：关联 Payment 之和减关联 Refund 之和；
- 未付：逐张 Invoice 的 `max(totalJmd - netPaid, 0)` 之和；
- BO 没有 Invoice 时可以显示在业务记录中，但不贡献消费金额；
- 取消 BO 不会凭空删除已经存在的财务文件，仍按实际 Invoice／Payment 展示；
- 车辆离店、BO 完工和 Invoice 付款继续是独立事实。

### 7.4 业务记录界面

每条记录至少显示：

- BO 编号和创建／业务时间；
- 关联车辆车牌和车型；
- BO 执行状态；
- Invoice 编号及最新版本；
- Invoice 总额、净已付、余额和付款状态；
- 进入 BO 详情的明确入口。

Invoice 仍在 BO 详情内部，不新增独立顶级路由。客户有多个车辆时，所有 `BusinessOrder.customerId === 当前客户 ID` 的记录统一展示，同时标明各自车辆。车辆后续转户时，不把旧客户的 BO 重新归给新客户。

### 7.5 Alicia UAT 一致性

`CUST-UAT-001` 必须提供真实可追溯的演示链：

- 14 个归属 Alicia 的 BO；
- 每个 BO 关联 `VEH-UAT-001` 或她名下明确车辆；
- 实际 Invoice 最新版本合计 JMD 532,000；
- 实际 Payment／Refund 净额合计 JMD 489,000；
- 实际未付合计 JMD 43,000。

客户详情显示的 14、532,000、489,000 和 43,000 必须完全由这些记录计算，删除客户静态摘要。若任何种子金额调整，页面应随同源数据自动变化。

车辆详情也使用同一事实链；不得再同时显示“关联 14 单”和“无业务单”。

## 8. 客户进入车辆后的返回逻辑

客户详情中的车辆链接使用显式来源 ID：

```text
/vehicles/VEH-UAT-001?fromCustomerId=CUST-UAT-001
```

车辆详情规则：

- `fromCustomerId` 有效且该客户与车辆存在关系时，顶部主要返回按钮显示“返回 <客户显示名>”；
- 页面刷新、复制当前 URL 或直接打开后，返回入口仍然有效；
- 参数无效或直接从车辆列表进入时，显示“返回车辆列表”；
- 不依赖浏览器 history，因为 history 在刷新和深链接时不可靠；
- 页面内仍可保留进入当前客户详情的关系链接，但不能代替顶部返回入口。

## 9. Mock API 与错误处理

接口按未来真实服务的合理形态设计，但实现继续在 Mock 层：

- 姓名预览返回规范化原名、对应音译、方法和规则版本；不支持时返回可识别校验错误；
- OTP 分为 request、verify、invalidate，不再使用一次点击的 `verify_otp`；
- KYC submit 和 verify 分开，无证据 verify 返回 400；
- 协议 sign 请求必须携带 medium 及该类型所需证据；
- 附件响应必须包含可访问 URL 与文件元数据；
- 客户业务摘要由共享 selector 派生，不创建第二份可写金额缓存。

至少使用稳定错误码 `CUSTOMER_NAME_TRANSLITERATION_UNSUPPORTED`、`OTP_PHONE_REQUIRED`、`OTP_CODE_INVALID`、`KYC_EVIDENCE_REQUIRED`、`AGREEMENT_EVIDENCE_REQUIRED` 和 `EVIDENCE_ASSET_INVALID`；页面文案可以中文化，但测试和未来后端接缝依赖错误码而非中文字符串。

所有失败都在原对话框内显示并保留用户已输入内容。重复提交使用幂等 ID，避免生成重复验证或签署记录。

## 10. 页面结构与交互

继续沿用当前蓝灰视觉和响应式卡片体系，不做无关重设计。客户详情顺序固定为：

1. 顶部客户身份与主要动作；
2. 正式资料（包含联系方式）；
3. 验证与协议证据；
4. 名下车辆；
5. 业务与财务摘要；
6. BO／Invoice 业务记录；
7. 风险条目、备注和审计历史。

验证三卡在桌面保持紧凑横排，手机纵排。每卡都同时回答三个问题：当前状态是什么、证据是什么、下一步能做什么。

键盘焦点、Escape 关闭、关闭后回到触发按钮、错误提示 `role=alert` 和 430px 无横向溢出继续作为硬性要求。

## 11. 持久化迁移

客户存储从当前 schema v2 显式升级到 v3；Linked Operations 从当前 schema v3 升级到 v4，以统一 UAT 客户／车辆 ID。两套存储按各自 schema 独立迁移。迁移要求：

1. 保留已有用户创建的客户、车辆关系、备注和审计记录；
2. 删除的字段不再写回，但关键旧值可保存在迁移审计摘要；
3. 缺少新双语字段的真实旧数据补安全默认值，不能因 guard 失败静默回种子；
4. 旧“已验证”但无证据的数据迁移为 `evidence_missing`；
5. 客户、车辆及 audit `before/after` 快照使用相同迁移规则；
6. 订单域固定演示客户和车辆改用客户档案的 canonical ID；
7. Linked Operations 的客户／车辆引用迁移后必须全部通过跨存储引用完整性校验；
8. 不清空 localStorage，不通过换 key 逃避迁移；
9. 迁移可重复执行且结果一致。

## 14. 验收标准

1. 所有现有双语演示客户的两侧姓名是同一姓名音译；Alicia 显示 `艾丽西亚·贝内特 / Alicia Bennett`。
2. 创建个人客户只有一个姓名输入框；中文安全生成拼音，英文只在完整姓名词典命中时生成中文。
3. 正式资料合并联系方式，来源、近期业务、近期业务时间、进行中业务、风险说明、标签和个人额外联系人全部消失。
4. 企业客户只出现一个可编辑主要联系人，不重复显示联系人列表。
5. OTP 显示验证号码和时间；号码联系不上可作废并完成新号码重验。
6. KYC 详情可打开真实合成驾驶证；没有证件不能核验。
7. 协议明确纸质或电子，并能实际调取对应证据。
8. 没有证据的旧完成状态显示“证据待补”，不伪装完整。
9. 客户进入车辆后有稳定的“返回该客户”入口，刷新后仍有效。
10. 客户和车辆业务历史按 canonical ID 读取同一 BO／Invoice。
11. Alicia 的累计消费、已付、未付、BO 数和业务明细互相守恒且可逐条进入来源 BO。
12. 所有新交互在桌面和 430px 可操作、可键盘访问，并通过类型检查、协作测试和全量 E2E。
