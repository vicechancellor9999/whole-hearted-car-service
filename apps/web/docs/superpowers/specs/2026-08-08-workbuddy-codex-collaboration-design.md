# WorkBuddy 与 Codex 协作开发设计

## 1. 目标

WorkBuddy 与 Codex 共同完成同一个 Whole Hearted Car Service 综合管理系统前端项目。双方共享一条 Git 主线，但各自在独立工作区开发，避免同时写同一文件造成覆盖。最终只有一个可运行、可验收的正式项目。

当前第一阶段目标是把经营概览仪表盘复原到指定照片的视觉结构，并使用用户提供的 WH Logo。已经明确的验收事项包括：四个维修班组卡片完整显示、上下两组指标卡对齐、卡片信息不缺失、实时时钟持续走动、浅色/深色外观可切换、用户身份位于导航栏底部、各指标卡可点击。

## 2. 不在本阶段处理的范围

- 不把本项目并入既有的 HTML-only 前端设计项目。
- 不覆盖 `/Volumes/公司文件/Whole Hearted 单文件 HTML 蒸馏版` 中的正式 HTML。
- 不在本阶段接入真实后端、真实支付、消息或身份认证服务。
- 不让两个代理同时修改同一文件。
- 不把代码、依赖、构建缓存或备份长期保存在 Macintosh HD。

## 5. 版本与分工模型

### 5.1 分支

- `main`：Codex 管理的集成分支；只有通过检查的提交可以进入。
- `agent/workbuddy`：WorkBuddy 的任务分支。
- `agent/codex`：Codex 的实现分支。

每次任务开始前，任务分支都从最新 `main` 同步。每次任务只产生一个范围清楚的提交；未通过审查的提交不进入 `main`。

该仓库仅在本机外置卷使用，不配置远程仓库，也不向第三方上传代码、参考图片或业务资料。

### 5.2 WorkBuddy 职责

- 接收由 Codex 在现有 WorkBuddy 对话中发送的单项任务包。
- 仅修改任务包列出的文件。
- 在自己的工作区运行指定检查。
- 返回提交哈希、改动文件、检查结果和遗留问题。
- 不自行合并 `main`，不同时启动第二个无范围任务。

### 5.3 Codex 职责

- 作为协调者确定每轮文件所有权和验收标准。
- 通过 WorkBuddy 界面直接发送任务、读取回复，不要求用户人工复制内容。
- 在 `agent/codex` 完成不与 WorkBuddy 冲突的任务。
- 审查 WorkBuddy 提交，运行集成检查，再合并到 `main`。
- 负责最终浏览器验收、同视口截图对比、响应式检查和问题归因。

## 6. 任务交换协议

Codex 发给 WorkBuddy 的每个任务包必须包含：

- 基线提交哈希。
- 任务目标和明确的非目标。
- 唯一文件所有权清单。
- 参考图片或文案的准确路径。
- 必须运行的命令与预期结果。
- 完成回复格式：提交哈希、文件列表、检查结果、未解决事项。

WorkBuddy 未提交前，Codex 不修改相同文件。若任务需要跨越双方已占用的文件，先结束当前任务并合并，再重新分配。

## 7. 迁移流程与回退

1. 再次确认 `/Volumes/公司文件` 已挂载且可写。
2. 在当前 WorkBuddy 对话中明确发送“暂停写文件”指令，等待任务处于完成状态；随后停止 `localhost:3000` 的 Next.js 开发进程并正常退出 WorkBuddy 应用，避免旧工作目录句柄继续写入迁移前目录。
3. 将 WorkBuddy 原工作区完整复制到 `snapshots/`，包含未跟踪的 `.env.local`，但不在日志中输出环境变量值。
4. 对源文件与外置卷快照做数量、大小和 SHA-256 校验。
5. 初始化 `main` 基线提交并创建两个代理工作区。
6. 将本机原工作区替换为指向外置卷 WorkBuddy 工作区的软链接。
7. 重新打开 WorkBuddy，从软链接入口恢复原任务并启动开发服务，验证页面、进程工作目录和文件读写位置。
8. 让 WorkBuddy 读取指定校验文件并回复当前提交，以证明它已进入共享仓库。

任何一步出现哈希不一致、软链接不可访问、WorkBuddy 沙盒拒绝外置卷或页面无法启动时，立即停止后续步骤。本机原目录在外置卷快照和新工作区均验证通过之前不会删除；回退时恢复原入口并继续使用迁移前快照。

## 8. 运行端口与缓存

- WorkBuddy 工作区默认使用端口 `3000`。
- Codex 工作区默认使用端口 `3001`。
- 集成工作区需要独立运行时使用端口 `3002`。
- 每个命令显式设置项目专用 `npm_config_cache=/Volumes/公司文件/Whole Hearted Car Service 综合管理系统_协作开发/.cache/npm`。

端口仅用于开发和视觉验收，不改变最终交付形态。不得复用正在运行的端口来掩盖工作目录错误。

## 9. 仪表盘验收标准

### 9.1 内容与品牌

- 导航栏使用用户提供的 WH Logo，文件哈希与参考文件一致。
- 公司名称显示为 `Whole Hearted Car Service Limited`。
- 绩效区域固定显示四个班组，名称、金额、目标和完成率完整。
- 今日营业收入包含工时、配件、月均对比和刷卡信息。
- 其余指标卡的标题、主值、副标题和明细项与参考内容一致，不出现用户未定义的“本城工单”等文案。

### 9.2 布局与交互

- 在与参考图相同的 `1920 × 841` 视口中，顶部、绩效区、第一组指标卡和第二组指标卡的列结构与参考图一致。
- 同一行卡片外框底边对齐；卡片内部明细区域的起始线和底部信息保持一致。
- 窄屏不溢出，内容按既定断点重排；不会因百分比高度循环依赖产生不同高度。
- 实时时钟至少跨两个连续秒值更新。
- 浅色/深色切换可用，用户身份固定在导航栏底部。
- 每个可点击指标卡具备键盘焦点、点击反馈和明确目标；占位页面必须明确标示，不能静默无响应。

### 9.3 工程检查

- 新行为先有能够失败的测试，再进行实现。
- `npm run lint`、类型检查、测试和生产构建全部通过。
- 浏览器控制台无未处理错误。
- 完成同视口视觉对比并生成 `design-qa.md`；P0、P1、P2 问题全部关闭，最终结果为 `passed`。
- 桌面视口和至少一个 `430px` 窄屏视口均进行真实浏览器检查。

## 10. 完成定义

协作机制只有在以下条件全部满足时才算建立完成：

- 两个代理实际读取同一 Git 仓库的不同工作区。
- WorkBuddy 原入口已经是外置卷软链接。
- WorkBuddy 能完成一个小型校验任务并提交，Codex 能审查并合并该提交。
- Codex 能在自己的工作区完成一个不冲突任务并合并。
- `main` 可以从外置卷启动并通过基础检查。

仪表盘阶段只有在用户可见页面通过上述内容、交互和视觉验收后才算完成；构建成功或端口可访问本身不代表完成。
