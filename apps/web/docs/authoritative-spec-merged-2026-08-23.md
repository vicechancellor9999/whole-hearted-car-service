## §2　系统总原则

1. 系统负责记录、计算、关联、筛选、提醒、追踪；**用户有最终决定权**。
2. 默认不阻止业务：缺料、未验证只提醒，不设门槛。
3. 合理的硬规则必须硬 —— 全系统只有这四条硬门禁：
   - 没有挂账资格却要挂账取车 → 绝对不允许（先开通资格再挂账）
   - 没有姓名 → 不能开客户资料
   - 没有手机号 → 不能开客户资料（可先填号暂不 OTP，验证以后补）
   - 手机号唯一、车牌唯一
4. 每单必挂正式客户（无散客）；BO / IR 只建在车辆上。
5. 改任何东西都留痕（谁、何时、前后值、原因）；**历史只增不改不删**。
6. 发给客户的内容必须支持中英文两版，由前台选择发送哪一版，且可自由编辑（不强制采用 AI 文案）。

### 2.1 最高优先级规则：记录提醒，绝不阻断业务

> 来源：`decisions/2026-08-14-record-remind-never-block-business.md`。原文写明"本决策是全项目业务交互的最高优先级规则"。

本系统是**业务事实记录、缺项提醒、后续跟进和审计留痕工具**，不是审批引擎，也不是业务闸门。

1. 资料缺失、尚未验证、相似候选、已过期、存在风险或流程未完成时，系统必须允许员工继续创建、保存、更新或推进业务。
2. 系统如实保存当前状态，显示清楚的 `待补` / `待验证` / `可能重复` / `已过期` / `异常提醒`，**不得把普通资料完整度提醒变成不可绕过的按钮禁用或 API 硬拒绝**。
3. 员工继续操作时，记录操作人、时间、缺失项和后续待办；不得伪造"已验证""资料齐全""无风险"。
4. 手机号可以不填；一旦填写，规范化号码只能属于一个客户。比较范围包括所有客户的主要号码、备用号码和 WhatsApp。同一客户可在自己的多个联系字段中复用同一号码，但不得把该号码保存给另一个客户。
5. 车牌号一旦填写并规范化，只能属于一辆车。
6. 姓名、Email、企业名称等相似候选只显示提醒，不能仅凭相似阻止建档。
7. OTP 未验证、驾驶证未上传、驾驶证四项未填完、企业联系人证据待补，均允许建档。
8. 除上述手机号/车牌唯一性、身份权限、安全边界及不可解析的技术故障外，**任何新规格、计划、实现、评审或测试都不得自行增加"不得创建""不得继续""必须审批后才能操作"等业务门禁**。

**与技术和安全边界的区别**：本规则撤销的是业务条件硬门禁，不撤销身份认证、最小权限、会话隔离、敏感数据保护；文件损坏/请求无法解析/存储写入失败等技术故障应明确报错并保留员工输入；幂等和并发保护只防止一次操作被意外重复执行，最终保存仍须重新检查手机号和车牌唯一性。

**产品表现**：主要操作按钮不因业务资料缺失而永久禁用；点击后先显示缺项摘要，员工可选择继续保存；提醒必须提供下一步动作；补齐后更新状态并保留前后审计，不删除原缺项历史；不新增主管审批、签字放行或其他用户没有要求的流程。

### 2.2 Mock-only 技术路线

> 来源：`decisions/2026-08-10-mock-only-no-real-backend.md`

1. 所有数据由 Mock API / 种子数据 / 内存持久化提供。
2. **禁止自行引入真实后端**：不接真实数据库、不实现真实鉴权、不接短信 / OSS / OCR 等真实外部服务。
3. 真实后端将由人类程序员另行接手开发。因此：
   - Mock API 的接口契约（路由、请求/响应结构、错误码、权限矩阵）必须保持文档化、稳定、可读，**作为后端接手的规格说明**；
   - 领域层与 Mock 层边界保持清晰，确保未来可整体替换为真实实现而不改动前端；
   - 重大接口变更前需在 docs 中说明理由。

**补充修订（8/10 08:27 同决策人）："不接真实服务"不等于"不做这些功能"。** 鉴权登录、短信通知、OCR 识别、附件上传等外部服务相关功能，**前端界面和完整交互流程必须照常做出来**：
1. 每个功能有真实可用的 UI，流程完整可走通演示。
2. 背后统一接 Mock 实现，代码中以清晰注释标记接缝（如 `TODO(backend): replace mock SMS provider`）。
3. Mock 实现的接口签名按真实服务的合理形态设计，未来替换零改动前端。
4. 禁止的只是"接真的"：不申请真实 API Key、不接真实 SDK、不连真实服务地址。

## §3　角色与权限

- **原型阶段：以超级管理员视角先做**；未来通过开设部分权限来区分岗位（8/17 定）。
- 权限设计参考 PRD 八角色矩阵：老板管理层 / 前台服务顾问 / 收银前台 / 维修工 / 维修组长 / 配件 / LiJian 国际采购 / 超级管理员。**财务岗位 = 收银前台，不另设。**
- 硬原则：
  - 没权限的接口**不返回数据**（fail-closed）。
  - 姓名 / 电话 / VIN / 金额是隐私。
  - 维修工**不可见**：客户联系方式、成交价、收付款、成本、利润、工资、他组绩效。
  - 维修工**不可改**：主状态、交单、收款。
  - 有权限即可看，**页面不搞角色专属视图**。

## §4　单据模型（8/17 定稿）

### 4.1 四种单据与归属

| 单据 | 归属 | 说明 |
|---|---|---|
| **业务单 BO** | 顶级 | **工单就是 BO，只有一种。** |
| **检查结果 IR** | 顶级 | **独立于 BO，两者互不隶属。** |
| **发票 Invoice** | 只活在 BO 详情内 | 独立编号、版本、金额快照、付款状态 × 结算安排双轴 |
| **报价单 Quotation** | 只活在 IR 详情内 | 独立版本 V1/V2/V3 |

- **BO 里的一定是 Invoice；IR 里的一定是 Quotation。**
- Quotation / Invoice **不占顶级导航**。
- **四种单据绝不混排。**
- 一辆车有多少 IR 和有多少 BO，**没有直接关系**。
- 报价单只用于跟客户磋商；客户同意了报价项目，前台**另外开业务单**，业务单不隶属于检查结果，**不强制溯源链**。
- **详情一律用独立路由页面，禁止居中弹窗**（`/customers/[id]`、`/vehicles/[id]`、`/orders/business/[id]`、`/orders/inspections/[id]`）。

> 来源：`decisions/2026-08-10-document-ownership-detail-pages-bo-actions-performance-value.md`（决策人傅立建，原话"定死了"）+ §15 裁决第 8 条。

### 4.2 BO 建单方式

前台针对**指定车辆**新建业务单 → 前台自然语言大白话输入 → **AI 拆成工时/配件双语收费项** → 人工可改 → 确认生成（8/16 定）。

**8/18 追加**：建单**先选车，客户自动带出（车→人）**；车辆搜索按车牌 / 车型 / 车架号 / 车主。

### 4.3 IR 建单方式

选车 → 自然语言回交检查结果 → AI 整理检查项目 + 报价草稿（工时报价、配件清单另报）→ 生成详情记录 → 前台人工发客户（A4 / PDF 三语）。

**IR 报价不记录客户逐项接受/拒绝**：报价只做磋商（版本 V1/V2/V3）；客户是否同意**以业务单 Invoice 客户签字为准**（8/18 定）。

写 IR 遇到配件价格未知时，向配件报价大厅发起协助申请。

> **8/20 废止的旧口径**：早期"BO 侧保留来源引用"和"§8 继续统计实施率"已废止。新流程只在 BO 普通备注写**可编辑、可删除的 IR 编号文本**，不建立结构化来源关系，也不据此计算实施率。

## §5　状态机

### 5.1 BO 业务单

```
待派单 → 已派单（等维修工接车接单）→ 维修中（等回单）→ 回单待审核 → 已交单（完结）
```

- **停滞**：接单后、交单前的旁路状态；维修工 / 前台都能标、都能恢复，全留痕。
- **回退一步 / 直接调整状态**：必须填原因，进审计。
- **交单**：前台核对绩效值（可改，记操作人）+ 施工班组（交单前随时可改派）；**交单时间决定绩效归属月份；交单是绩效计入唯一触发点，只算一次**。
- **取车不占 BO 状态**，归停车费 / 交车模块。
- **里程**：不接车时登记。维修工接走后负责记录里程（每单开始前记录）；车辆详情显示最近一单 BO 的里程。
  - 8/18 追加：**接车接单不带里程**，接单 = 车进厂，里程接单后再补录（详情页补录按钮）；详情 / 打印显示记录人与时间。

### 5.2 Invoice

`未付款 / 未付清 / 已付清` × `正常 / 挂账（未付款挂账 / 未付清挂账）`

- 已付清完结。
- **车开走不等于钱付清；欠账不把 BO 退回未完结。**

### 5.3 IR 检查结果

```
新建（前台录纸质单 / 维修工端回传）→ 审核并创建报价 → 发送客户 → 待客户回复 → 客户已回复（完结）
```

- 账龄 **2 天黄、4 天红**，持续催收，**不闭环不下榜**。
- 详情页（`/orders/inspections/[id]`，8/17 落地）：状态链 + 内部检查提交（原文/署名，内部证据）+ AI 整理草稿 + 已整理检查项目 + Quotation + 执行率 + 客户沟通记录（可新增，交付/回应分别留痕）；列表点击报告编号或"详情"进入。
- 状态链末两步由沟通记录推导：已发送且无任何回应 → `待客户回复`；已发送且存在非"暂无回应"的回应 → `客户已回复`。
- 实际实现的五步 Chevron 步骤条：`维修工提交 / AI 整理 / 前台审核 / 已出报价 / 已发布`。

### 5.4 车辆

`在厂 / 不在厂 / 超时未取车`

- **闭环定义（8/17）：车还没离场，这辆车就还没闭环。** 不是没有业务单就闭环 —— 维修工报告写不清楚、报价模糊客户无法理解，是车辆滞留的主要原因；**车还在厂，责任就还在**。
- 取车提醒条件：车辆在厂 + 相关 BO 都已交单（无下一步可执行 BO）→ 系统提醒前台执行通知取车（见 §10）。
- 在厂但从未建过 BO：显示"在厂车辆没有业务单，请检查"。

### 5.5 客户

- **有账单 ≠ 有欠账。**
  - 有账单 = 存在 Invoice（在途）
  - 有欠账 = 存在未付款 / 未付清 / 挂账未清 Invoice（讨债对象）
- 所有未完结事项必须有人跟踪到完结。

## §6　收费与金额

- 顶级分类：**工时 labor / 配件 parts / 其他服务 other_service**（停车超时、拖车、外派、其他）。
- 折扣、减免、冲销、四舍五入是**金额调整**，不伪装成收费项目。
- 每个 Invoice 版本：工时 + 配件 + 其他 + 调整净额 = 总额（**金额守恒**）。
- 金额精确数值 + 币种 **JMD**；工资口径 **CNY**。
- 收款、付款分别汇总不合并；多币种分别汇总不混算。
- **单价 = 最终价，含 15% GCT，不再另算。**
- 维修工回交缺项（里程 / 照片等）：填原因后仍可提交，不硬拦。

### 6.1 绩效值口径（8/18 老板修正）

> **绩效值是独立计算值，默认 = 工时合计，配件不算绩效。**
> 原实现误把配件计入，已修正代码与种子。

- 每张业务单有"整单绩效值"（JMD）：系统按已确认项目计算默认值，允许手工调整（调整只改绩效值，不改执行或财务状态，必须留审计）。
- **正式交单 = 绩效计入的唯一触发点**：未交单"待计入"，交单后"已计入"。
- 绩效只归班组，**不显示个人金额**。

## §7　编号、双语与打印

### 7.1 编号

| 单据 | 格式 |
|---|---|
| BO | `KGN-WH-2026080919422` |
| IR | 带 `-IR-` |
| Quotation | 带 `-QT-`（版本 V1/V2/V3） |
| Invoice | 带 `-INV-`（版本另记） |

`KGN` = 门店码（曼德维尔分店换码）、`WH` = 品牌、牙买加业务日、尾号服务端原子递增。

### 7.2 双语

- 客户姓名 / 车型中英双字段，**中文主显示**；表单输一侧自动翻译另一侧（音译规则）。
- AI 拆单时每条收费项目同时产出中英双语（人可改）。
- 8/18 追加：**备注 = 中文留档 + 英文客户联两栏**（翻译人可改）；详情 / 列表 / 打印中英双名。

### 7.3 四联 A4 打印（8/17 定案）

| 联次 | 内容 |
|---|---|
| **中文客户联** | 完整 |
| **英文客户联** | 完整 |
| **维修工联** | **不显示价格**，带施工勾选 + 检查结果 + 签字栏，回交后前台代录 |
| **中英参照联** | 留档 |

## §8　收付款与退款

### 8.1 基本口径

- 财务独立：**未付款 / 未付清 / 已付清由收退款推导**。
- 取车归停车费模块。
- 8/18：收付款工作区新增**退款入口**（上限 = 已收 − 已退）。
- 收付款页 `/payments` 汇总五张卡：应收 / 已收 / 待收余额 / 有欠账客户 / 待通知取车 + 付款状态筛选 + 搜索；行点击进 BO 详情原地收款。

### 8.2 退款规则（8/18 老板定）

1. 退款必须写明**退的是什么款**（工时费 / 配件费）+ **具体项目** + **方式**。
2. **对冲对冲的是绩效值**：
   - 跨月已交单的**工时费退款 → 自动开对冲单**（退多少对冲多少，即对冲对应工时绩效，负绩效计入本月）
   - **配件费退款不冲**（配件不产生绩效）
3. **当月已交单必须先取消交单才能退。**
4. 每笔退款自动生成**退款单**（`receiptNo`）；退款单打印给客户签字 + 拍照回传留档（可选，不签不影响流程）。
5. 四联打印的付款记录标明退款类别。

### 8.3 取消交单与派生单（8/18 老板定）

- **取消交单：仅当月。**
- 跨月发现问题 → 两选一：
  - **售后单**：修好，不计绩效值
  - **对冲单**：负绩效值扣回原单，计入原班组当月
- 两单都关联原工单（`linkedOrderId`）。

### 8.4 独立收付款事实（8/22 老板裁决）

> 来源：`specs/2026-08-22-independent-payment-refund-records-design.md`。裁决原文：every payment and every refund is an independent data record.

**每一笔收款和每一笔退款都是独立的、只追加的业务事实。**

1. 一笔收款永不覆盖、吸收或成为另一笔收款/退款的一部分；退款同理。
2. 生命周期操作永不删除、编辑、合并或隐藏收付款事实。任何收款、退款（含零现金的应收冲减）、历史退款占用、停车退款历史或已付清标记，都会**使新的作废操作不合格**。
3. 本轮不提供通用的收付款更正命令。若日后批准更正，必须**新建一条补偿事实**，永不编辑或删除原事实。
4. **合计与余额是对独立事实的投影**，不是替代它们的持久化字段。
5. 迁移一对一保留每条既有事实，永不合并记录、永不由一条推断另一条。
6. 精确幂等重试返回原事实/原结果；真正的新意图创建带新 mutation ID 的新事实。
7. 切换前嵌入式的历史数组成为不可变历史；切换后创建的每笔收付款（包括由 `legacy_quick` 单据持有的）都是新的只追加 v2 事实。停车更正归属不变。

## §9　挂账（登记制 · 8/17 定案）

1. **客户级挂账资格**：前台打开签名面板 → 找管理员现场签 → 前台提交 → **即时生效，无审批流**；记录客户、签名笔迹、登记前台、时间。前台可撤销（填原因），撤销不删历史；重新开通需重新签名。
2. **逐 Invoice 签账**：每张实际挂账的 Invoice 由客户针对**单号 / 版本 / 余额 / 日期 / 语言**签字确认。**资格签名不能替代逐单签账。**
3. **无挂账资格 → 不能挂账取车（硬规则）。**

**办理取车**：付清放行；有余额必须挂账 —— 无挂账资格硬拦（提示先开通资格或收款结清），有资格需客户签账（签字板 + 语言版本）后放行，取车事实留痕。

## §10　停车费与取车通知（8/17 定案）

### 10.1 通知取车流程（前台手动执行）

1. 系统 AI 起草提醒文案，**永远产出中英两版**，内容包括但不限于：车辆状态、已完成的服务内容概述、未付账单金额、最迟取车日期（= 通知次日）。
2. 前台选择发哪一版（中文或英文），**文案可自由编辑，可以不采用 AI 起草的内容**。
3. 通知渠道：**Twilio 短信**（发到客户 OTP 手机号）/ **WhatsApp 链接** / **Email**（有邮箱才发）。
4. 这些通知动作是人工做的：**至少完成一项，前台说做了就是做了**，在系统里记录完成 → 开始记时（记通知完成时间 D）。不强制全部渠道都发。

### 10.2 计费日历

```
D（通知完成日）→ D+1 宽限日（免费）→ D+2 起 JMD 2,500 / 自然日 → 取车日不计费
                                    ↳ 每 3 天提醒发停车费账单，直到登记取车
```

- 后续提醒**不重置**首次通知日。
- 门店临时不开门走减免，**不改公式**。
- **系统只提醒员工，绝不自动发消息给客户。**

### 10.3 减免

- 全额免除 / 按整数天。
- 保留：原始天数金额 + 减免天数金额 + 原因 + 经办人 + 时间 +（如需要）管理员签名 + 最终应付。
- 同一案件累计减免 **≤ JMD 50,000 前台自行处理；> 50,000 管理员现场签名**。
- **禁止拆分多笔规避。**

### 10.4 停车费收款即开票（8/18）

每个未结清案件都有收款按钮；收款同时生成停车费 Invoice（`other_service · parking_overtime`，含减免调整）。发票页显示账单金额 / 已付 / 未付 / 余额 / 历次付款记录，可打印。

案件由 `pickupNotice` 派生（`src/lib/api/mock-quick-parking.ts`，独立 `wh_quick_parking_v1` 存储）。

## §11　绩效

### 11.1 指标公式

```
员工携带指标 = 月标准工资 ÷ 提成比例（当前 25%）× 汇率（当前 23）
班组指标     = 全员之和
```

### 11.2 规则

- **完成率只算班组**，不显示个人完成率 / 金额 / 排行。
- 工资测算 = 标准工资 × 班组完成率（最低 0），**只测算不记发放**。
- 规则版本化：改比例 / 汇率新建版本 + 生效月份 + 四组影响预览；**已锁定月份永不重算**。
- **正式交单 → 记入交单月份班组绩效**；未交单 = 待计入；已计入可更正（留原值）。
- 查看数据不签名（有权限即可看）；**维修工在维修端查看才需签名确认**。
- 历史对比只用已锁定完整月份；入职首月按天折算不乘完成率；月中离职按天折算后乘完成率。
- 月度锁定前需操作者显式确认"已核对正式交单、班组、绩效值及工资测算"。

### 11.3 班组

> §15 裁决第 6 条：旧制 T1–T7 **作废**。

现制四组：**车间一组 / 车间二组 / 工程机械组 / 钣金喷漆组**。各组成员名单待老板提供（现用旧制 T1-T7 名单暂代）。

**派单界面（8/18）**：班组卡片 + 车间一组/二组一键轮换；**工程机械组派单必须落到具体维修工**（暂用名单：陈少松 / 李军军 / 曹琪 / 邱启发，待老板更新正式名单），不选人不能确认，**API 硬拦**。

## §12　客户与车辆

### 12.1 客户

- **必填：姓名 + 手机号**（8/17 定：必须先填）；OTP 候补。
- 驾驶证识别（姓名 / 生日 / 性别 / 地址，选填，**无证不拦**）；机构客户走主要联系人驾驶证（非强制）；**公司地址与联系人地址分开**。
- 客户详情：正式资料（含联系方式合并）、账单明细（每张 Invoice 欠多少红字）、当前/历史车辆、验证证据、备注（可随时编辑）；挂账资格双入口（开通/取消）；审计收修改历史小标签；**无新建 BO/IR 入口**。
- **无散客，每客户必建档**；疑似重复只提醒，人工决定建新 / 返回 / 合并。
- **手机号唯一。**

**OTP 证据缺口口径（§15 裁决第 12 条）**：登记时"未发起 OTP"是**合法候补状态**（详情显示"待补验证"，不是"证据待补"）；只有旧数据无证据完成、或手机号缺失才显示"证据待补 / 手机号待补"。

### 12.2 车辆

**字段**：车牌 / 车架号 / 发动机号 / 品牌 / 型号 / 年款 / 颜色 / 车身类型 / 座位 / 排量 CC / 燃油 / 里程。

> §15 裁决第 1 条：**没有变速箱字段**（定案删除）。
> **不管登记到期**（政府的事）。

**车辆档案**：车证照片 + 全部相关照片（维修故障照片入档案）、消费总额、历史 BO/IR/Invoice、当前客户、停车事实。车辆也显示自己的账单，但**债务主体是客户**。

**车牌唯一**（重复直接定位已有车）。

### 12.3 车辆-客户关系

> 来源：`decisions/2026-08-10-vehicle-current-customer-confirmed.md`

1. **保留关系历史**：车辆与客户的关系历史完整保留，带起止时间，任何历史关系不可删除或改写。
2. **一车一位当前客户**：每辆车同一时间最多一个 `endedAt = null` 的当前客户，**允许暂时没有当前客户**。
3. 换绑在**同一原子保存**中结束旧关系、建立新关系；旧工单、费用、照片、收付款归属保持原样，**不回写历史客户**。

### 12.4 欠账归并

客户欠账归并：已交单未结余额，**ID 直配 + 手机号兜底**（`src/lib/customers/debt.ts`）。

## §14　BO 作废语义（8/18 老板定）

> 来源：`decisions/2026-08-18-bo-void-semantics.md`

### 14.1 一句话定义

**作废一张 BO = 这张单从系统里"不存在于任何计算口径"，但单据本身保留可见、留痕、可恢复。**

不是删除：列表仍能看到（置灰 + 已作废徽标），详情页有红色横幅与恢复按钮。

### 14.2 作废后逐口径行为

| 口径 | 作废后 | 实现位置 |
|---|---|---|
| 绩效汇总（已计入/待计入，按交单月归属） | 整单绩效值退出统计；对冲单为负绩效，一并退出 | `summarizeQuickOrderPerformance`（跳过 `voidedAt ≠ null`） |
| 工资测算 / 规则预览 | 走绩效汇总快照，随汇总自动剔除 | 绩效模块 |
| 财务（应收/已收/余额/退款） | 不计入收付款工作台合计、欠账、财务桶 | `payments-workspace`、`debt.ts`、`workbench-state.ts` |
| 客户档案（欠账/累计消费/账单数） | 不计入 | `debt.ts` |
| 工作台提醒（待派单/维修中/…/欠账/取车） | 不计入任何桶 | `computeWorkbenchReminders` |
| 停车费案件 / 待通知取车 | 不计入；取车通知按钮消失 | `parking-workspace`、`vehicleHasOpenQuickOrders` |
| 列表状态 chips 计数 | 不计入（"全部"仍含作废单，因为不删除） | `business-orders-workspace` |
| 派生单据（售后/对冲） | 作废原单时联动一并作废；恢复原单时联动恢复 | `applyMockQuickOrderAction void/restore` |
| 取车 / 付完全款（完结三件事） | 随单无效；恢复后原样回来 | 同一单据 |
| 收款/退款/补签字/改内容/打印 | 全部禁用（API 层拦 + UI 隐藏）；恢复后解禁 | `mock-quick-orders.ts` 各守卫 + 详情页 |

### 14.3 作废门槛（两级）

1. **权限：不设限。** 谁都能作废（只要填原因），前台 / 维修工 / 财务同权。
2. **资金：设硬门槛（8/18 修正口径）。有付款记录的不能作废** —— 钱已动过，只能走退款 / 对冲处理。无付款记录的可作废（欠账随单核销）。
3. **信息透明（不拦但明示）**：作废弹窗动态提示 —— 已交单则写明"绩效将从 X 月统计退出"；已完结则加"撤销完结事实"；跨月则加"该月份报表已出"。

### 14.4 不受作废影响（有意为之）

- 收入统计页（`mock-revenue`）是静态演示流水，本来就不从 BO 推导。
- 绩效模块的"锁定快照 / 工资测算"是静态演示数（`AUGUST_ACTUAL` 硬编码），不从 BO 实时推导；作废通过绩效汇总卡体现。
- 派单轮换指针（一键轮换）只记录"点了按钮"这个事实，不回滚。
- 单据历史（`statusHistory`）只追加不删：作废 / 恢复都是追加记录。

### 14.5 恢复

撤销作废标记，全部口径原样重新参与计算；被联动作废的关联单按原因标记联动恢复。

1. **先方案后代码**：动页面结构前先出静态示意 / 文字方案，老板点头再动手。
2. **老板说改哪就改哪**，微调不做重排，**不擅自扩大范围**。
3. **有分歧要反驳并给专业建议，不无脑顺从；不无限抬杠。**
4. **交付 = 能点开的页面 + 桌面/430px 截图 + 测试全绿；文档不算完成。**
5. 提交前：`typecheck` + `test:collaboration`；改页面行为必须全量 e2e；离开前必须提交。
6. dev 服务用托管后台任务常驻 3210；同一 worktree 禁双 dev server；不动 `.next.bak-*`。

### 16.2 仓库协作规则（AGENTS.md，2026-08-10 起）

- **直接在 `main` 分支上工作。不要创建新分支，不要创建新 worktree。** 本仓库只有一个工作区：`main/` 目录。
- 提交前必须通过 `npm run typecheck`、`npm run test:collaboration`；改动页面行为时必须同步更新 e2e 并全量通过。
- **工作中途离开前必须提交**；不得在 main 工作树遗留无法通过 typecheck 的半成品文件（2026-08-10 曾因此阻塞全仓验证 6 小时）。
- 历史分支内容在 `archive/*` 标签中查找；回滚基线见 `backup/pre-integration-20260810`。

### 16.3 验证命令

```bash
pnpm run typecheck
pnpm run test:collaboration
pnpm exec playwright test --config=playwright.unit.config.ts
E2E_BASE_URL=http://127.0.0.1:3210 E2E_REUSE_SERVER=1 pnpm exec playwright test
```

dev server：`pnpm exec next dev -p 3210`（固定 3210；起服前先清 `.next`；同一 worktree 禁双 dev）。
