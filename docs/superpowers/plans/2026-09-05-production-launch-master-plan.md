# Whole Hearted 上线实施总计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement approved work packages task-by-task. 本文件是项目级上线计划，不是对所有实现、付费服务、数据迁移和上线切换的预先授权。每阶段开工前拆出可独立审查的实现任务；不要把本计划当成已经完成的记录。

**Goal:** 将 Whole Hearted 做成当前门店员工可日常使用、独立程序员可审查接手、可在云端持续运行并安全迁入选定 Lark 业务资料的管理系统。

**Architecture:** 优先保留经审查可用的业务服务与数据，重构职责混杂的核心界面和接口边界。采用单一 Web 应用、按业务模块组织的后端、PostgreSQL、私有附件存储，以及按需要增加的持久后台任务；先服务单店，为分店留下明确的数据和权限边界。

**Tech Stack:** 当前仓库为 Next.js / React / TypeScript / PostgreSQL；本计划不要求为了重做界面更换技术栈或引入微服务。具体部署供应商、规格、费用在容量盘点后由工程负责人提交方案，不在本文虚报预算。

**Spec:** 以用户本任务的明确业务要求为首要输入；既有业务基线及总验收清单标注“未批准”，只能当历史材料。已批准单应用边界见 `../specs/2026-08-27-3210-canonical-single-app-design.md`；当前证据见 `../../qa/2026-09-05-core-paths-closure-audit.md` 和 `../../qa/2026-09-05-programmer-review-entrypoint.md`。本计划中的建议、工期和服务指标均待阶段 0/1 评审定版，不伪称用户已经批准。

## 0. 现在的结论与下一步

**不再以持续堆补丁作为推进方式，也不未经审查整仓重写。先审查、定业务验收和核心交互，再按模块实施。独立程序员从阶段 0 介入，不等代码全部写完才第一次看。**

下一步就是完成阶段 0 的审查包和阶段 1 的业务验收图；不需要用户先学编程，不需要先买服务器或 NAS，不以重新登录 3220 作为全部规划工作的前置条件。真实界面最终验收仍需有效登录和隔离验收环境。

“上线”是员工用它处理业务，数据可恢复、失败可纠正、有人维护，不是部署一个能打开的网页。Lark 在正式切换前继续承担当前业务，迁移范围和停写窗口单独批准。

## 1. 首次上线的范围

### 必须交付

| 模块 | 员工实际要完成的事情 | 首发交付边界 |
| --- | --- | --- |
| 客户与车辆 | 查找、建档、区分车主/联系人/费用承担方、查历史 | 个人/公司、联系人、车辆分别建模；历史订单保留当时责任主体，不因改车主改变历史 |
| 检查结果 | 收原始回单、整理检查建议和报价、出报告、跟进 | 独立于业务单，可选关联；AI 原文与草稿可对照；中文、英文、对照版本 |
| 业务单与维修轮次 | 确认工作和费用、派工、记录实际工作、交单、返修 | 一单多轮；每轮人员、绩效、回单与历史可追溯；更正/撤销路线完整 |
| 单据 | 费用责任确认、施工依据、收款/退款凭证 | 办公室联和客户联同内容同语言成套生成，两联分别起页；维修工联突出工作和本单本轮绩效；收退款独立凭证 |
| 收付款 | 逐笔登记、查看余额、退款或纠错、补打 | 金额由正式事实复算；重复提交不重复记款；修改费用不静默改旧凭证 |
| 在场车辆、取车与停车费 | 记录通知和离场、计费、暂停、免除及结算 | 时间、费率、免费期、责任人、历史快照和异常处理明确 |
| 员工、班组和绩效 | 发账号、分工、设基准工资、查目标和调整 | 不加入擅长车型等无关字段；旧班组/空班组有迁移方案；个人账号与历史作者分开 |
| 客户通知与内部协调 | 发通知、看发送结果、安排跟进、业务内留言/@提醒 | 优先接用户已有短信接口；通知状态真实；业务内协调即可，不另造通用聊天平台 |
| 工作台与统计 | 看今天待处理、异常、在场车辆、收付款和绩效 | 每个数可下钻并复算；数据来自正式后端，不从 Mock 拼出看板 |
| 超级管理员后台 | 管人员权限、门店信息、AI、通知、附件与备份配置 | 配置有生效状态、测试入口、错误提示、权限、审计与安全的凭据处理 |

### 不作为首发范围

- 内账、报销、配件采购，按用户要求交给另一个系统；旧菜单和可达入口也要审查隔离，不只是视觉上藏起来。
- 向其他修理厂售卖的多租户平台、订阅收费、复杂总部体系。
- 依赖未经核实能力的 WhatsApp 个人账号自动读写。正式接入可行性、权限和费用另行验证；首发不能依赖尚未确认的集成。
- 完整离线写入和多端离线冲突合并。首发必须支持弱网提示、草稿恢复与重试；不宣称断网时业务已经保存成功。

这里没有把停车、绩效、迁移、通知或管理员后台移到“以后再说”；它们都在首次完整上线计划内。

## 2. 全局约束：已明确的业务与交互要求

- 使用用户提供的 WH 正式 Logo 与品牌素材，不自行重画替代。
- 电脑、iPad、手机都属于正式交付；响应式不是把电脑页面等比例缩小。
- 顶部紧凑导航，业务信息放在适合操作的明细区，避免巨大的装饰头部占据首屏。
- 工时/配件明显区分，保留其他费用类别；名称与描述分开，分类合计及总金额明确，金额不换行；工时单位 JOB，新录 QTY 为整数，不篡改历史小数数量。
- 办公室联与客户联同内容成套输出；用户选中文就整套中文，选英文就整套英文。它们确认费用和责任，不冒充收据或报税凭证。
- 维修工联展示本单本轮工作及绩效；后续轮次不自动复制整单工时绩效，授权调整有明确入口与记录。
- AI 负责提取、整理、翻译、建议分类；未明确的价格/类别标待核，不猜成正式收费。人工可编辑、拒绝、撤回 AI 草稿，不覆盖原回单。
- AI 有真实等待状态、停止/超时/失败、草稿保护和受权限隔离的缓存。取消前端等待不承诺供应商已经停止计费。
- 普通资料欠缺显示待补/待验证/提醒，并保留处理责任；不能普遍变成业务操作死路。已填写的标准化电话、车牌重复，以及越权、损坏输入、无法安全保存是不同的完整性/技术边界。
- 每个错误至少说明：是否已保存、哪些内容保留、下一步按钮、需要谁处理；不能只报“未完成，稍后再试”。
- 管理员能纠正错误并追溯原记录；AI 不越过人的决策，系统不通过偷偷改历史来制造表面一致。

## 3. 需要集中定版的规则，而不是开发中暗自决定

阶段 1 整理成一页决策表，给出实例和推荐答案，由用户/业务负责人一次评审。未确认前不擅自改变真实金额、权限或历史。其余界面实现细节由执行者负责。

| 决策 | 现有问题 | 推荐评审方案 | 最晚决策点 |
| --- | --- | --- | --- |
| 折扣口径 | 旧文件一个要求仅逐项，一个写整单折扣；服务当前把整单折扣输入置零 | 新操作优先逐项折扣、分类汇总；历史整单折扣单独识别兼容，不能静默丢弃 | 收费实现/迁移前 |
| 错误记录如何撤销/作废 | 有正式文档或客户沟通时存在删除阻断 | 先明确无效事实的作废/解除引用、原始留档、权限原因与外发副本标记；财务与绩效按更正事实处理；提供可执行路径 | 删除与纠错验收前 |
| 绩效月份与调整 | 有旧跨月/同月规则和后续用户调整要求 | 用首轮、返修、跨月、负调整、历史工资修订五个算例，确定生效月份及汇总口径 | 绩效实现/迁移前 |
| 取车与停车 | 旧材料有业务硬阻断，用户强调人能处理异常 | 明确多单、欠款离场的提醒/授权责任，免费期、起算、暂停和免除；不直接把旧基线当合同 | 停车与权限验收前 |
| 历史身份不明 | 旧班组为空/合并，客户归属缺失；现有表约束不全支持未知状态 | 保留原始信息和待认领状态；迁移暂存隔离或经评审的数据模型修订，不猜身份、不强造登录账号 | 迁移试导前 |
| 迁移保留范围 | 重复字段、统计字段、评论/历史可导出程度未核实 | 每列分类，逐项确认保留/计算/合并/归档/不迁；来源缺失不伪造历史 | 全量演练前 |

## 4. 产品和工程怎么设计

### 4.1 员工看见的是任务，不是技术模块

- **前台工作台**：待接待、待核对报告/报价、待派工、待交单、待回复、待收款/取车；可直接进入对应业务位置。
- **维修工手机端**：班组任务、当前车辆、工作清单、拍照/回单、本人相关绩效；不要求在大表格中横向寻找按钮。
- **老板视角**：当天进度、异常、收付款和绩效，数字可追溯到原记录；权限可由管理员配置。
- **管理员**：账号权限、门店和规则版本、集成状态、迁移映射、备份与审计。危险配置不把密钥全文返回浏览器或日志。
- **业务单详情**：紧凑身份区和顶部标签；费用/工作范围与维修/收款动作关联清楚，独立滚动不产生假空白。单据阅读占主要空间，手机提供连续阅读和明确缩放。
- **检查详情**：原回单、可编辑结构化草稿、报价核对、正式报告与客户跟进相互连通；不是把一句描述当项目名称。

必须交付的原型不是登录页海报，而是工作台、客户/车辆查找、业务单、检查编辑、单据阅读、维修工手机任务、关键纠错弹窗。先评审层级、信息密度、操作路径和金额可读性，再铺全系统风格。

### 4.2 模块化单体，而不是另造复杂平台

```text
电脑 / iPad / 手机
        ↓ HTTPS
唯一 Web 应用：页面 + 正式 API + 服务端权限
        ↓
客户车辆 | 检查 | 业务单维修 | 收付款 | 停车 | 绩效 | 通知协作 | 管理
        ↓                              ↓
PostgreSQL：业务事实、版本、审计       私有附件存储：照片、原回单、PDF
        ↓
必要的持久任务：AI / PDF / 通知（可重试、可查询，防重复副作用）
```

- 前端负责展示、输入和草稿；后端统一权限、金额、状态、编号、事务、幂等和历史。前端预览复用规则契约，不独立创造一套账。
- 沿用 `apps/web/src` 和 `@formal/*` 边界，服务端凭据/数据库代码不能打进客户端。后端按业务聚合拆职责，不按文件行数机械分割。
- 关键写入区分保存成功、明确失败、结果未知；对未知结果查回执/原请求，不靠重新生成编号重试。
- 生产业务数据不能回退 Mock。Mock/样例留给明确隔离的开发测试环境，不能以“返回空列表”掩盖正式接口失败。
- 分店先确定客户/车辆是否共享、订单/班组/权限/编号/时区/设置如何按店归属，再设计可扩展模型；首发仍是一家店，不强做 SaaS 多租户平台。
- 附件采用私有对象存储是当前建议：数据库存元信息和引用；访问经鉴权，设容量与预算提醒。NAS 后续作为额外备份，不成为首发访问必需环节。

### 4.3 可审查、可维护的交付要求

- 每个改动包只解决一个可说明的业务问题，包含代码、迁移（如需）、测试和验收结果；不用一个巨大提交混合整套系统。
- 大组件重构先补行为测试，再按收费、轮次、文档、恢复等职责拆分；不同时偷偷改变业务规则。纯结构调整与规则调整分开审查。
- 每个包由独立程序员审查服务端权限、事务、数据兼容和代码结构；AI 自审不替代人审。
- 建立一份当前规则表、一份当前发布验收表、一份风险列表；历史交接日志保留，但不继续复制成多份互相矛盾的“最新规范”。
- 提交边界要核对已有未提交改动的所有者和依赖，不直接 `git add .`，不删除未知改动。
- 开发、预发布、生产的数据库、附件、密钥和消息收件人隔离；真实客户数据不用于日常故障注入。
- 开发产物全部留在外置卷；一个活跃构建加一个确有用途的验收构建，过期 QA 产物按清单处理；备份单独定义保留期、验证恢复后再按授权清理。容量/日志轮转和配额都要有负责人。

## 5. 分阶段实施与验收

阶段完成靠证据，不靠日历到了。建议资源：一名负责工程交付的资深全栈程序员，Codex 协助实现/测试，独立审查时间，前台和维修工代表参与业务验收。只有 AI 持续工作、无人负责工程审查时，不给出可靠上线日期。

### 阶段 0：保护基线并完成技术诊断（建议 3–5 个工作日）

**负责人：** 工程负责人，Codex 提供盘点和证据；独立程序员审核。

- [ ] 对当前源码、未跟踪文件、迁移、依赖、运行配置和生成物分类；记录当前版本及“工作树不等于 HEAD”。
- [ ] 核实已有备份是否覆盖数据库、附件和配置，先在隔离位置恢复验证；不为保险无上限复制整个依赖和缓存。
- [ ] 按三类出处理清单：可保留、需要重构、需局部重写。每项给原因、影响、测试保护和工作量，不以“代码很多”判死刑。
- [ ] 盘点首发入口的正式/Mock/占位状态，建立风险清单，标明金额/权限/丢数据风险优先。
- [ ] 给程序员一份能复现的启动、测试和目录说明；审核后建立候选交付基线。

**交付：** 基线清单、恢复结果、模块处置表、风险优先级、第一批工程任务。

**通过条件：** 独立程序员能找到唯一候选源码、理解运行方式、复现关键测试、解释哪些必须重构；备份不是“文件存在”而是恢复成功。

### 阶段 1：定业务规则、异常路线和交互原型（建议 3–5 个工作日）

**负责人：** Codex/设计实施者整理；用户确认实际经营做法；工程负责人评估可实现性。

- [ ] 将第 3 节的分歧集中定版；给每项一条正常例子和一条纠错例子。
- [ ] 绘制从查客户/车辆到离场的业务关系，明确检查可独立、收款时点可早于交单，不把流程强做成唯一向导。
- [ ] 交付第 4 节关键页面电脑/iPad/手机原型，使用真实风格但虚构业务数据；包含长项目名、空数据、错误、未保存和加载状态。
- [ ] 交付办公室/客户成套、维修工、收款/退款、检查报告的纸张样例；查看实际 A4 输出与屏幕阅读效果。
- [ ] 为第 8 节每个场景明确入口、操作者、结果、错误处理和验收证据。

**交付：** 当前业务规则表、权限矩阵、可点击核心原型、单据样例、验收用例。

**通过条件：** 前台和维修工能按场景指出“从哪里开始、下一步做什么、错了怎么改”；用户对关键交互和单据认可。审美验收不能由程序员或测试数字代替用户。

### 阶段 2：工程底座与云端预发布（建议 5–8 个工作日）

**负责人：** 工程负责人；独立程序员审查。

- [ ] 固定唯一正式数据入口，清理首发范围中的占位/Mock fallback；隔离内账采购旧入口。
- [ ] 建立开发/预发布/生产配置界限、正式认证的隔离 E2E、持续集成构建和版本标识；从干净检出能复现。
- [ ] 新建独立云生产启动方式，真实域名/HTTPS、数据库连接和持久化配置；数据库迁移从普通应用启动中分离为受控发布步骤。
- [ ] 数据库不直接向公网开放，使用私网或严格限定可信来源；应用运行账号与迁移/备份账号分权。检查发布包不夹带 `.env`、真实备份、验收业务附件或密钥；在 HTTPS 入口验证可信代理、会话与写请求来源检查。
- [ ] 接入私有附件存储适配，保留本地测试适配；验证鉴权、文件类型/大小、失败重传和数据库/附件一致性。
- [ ] 打通实际发布应用的健康检查、错误日志、容量和备份失败提醒、日志轮转；日志不泄露密钥与敏感原文。
- [ ] 建立备份/恢复与版本回退运行手册，在隔离环境演练。

**交付：** 可重复部署的预发布环境、测试流水线、配置清单、备份恢复和回退记录。

**通过条件：** 应用与服务器重启后记录/附件仍可访问；外部未授权访问被拒；从备份恢复到空环境成功。不是只验本机 3220。

### 阶段 3：做透一条真实业务闭环（建议 7–10 个工作日）

**负责人：** 实施程序员/Codex；前台和维修工代表验收。

- [ ] 查/建客户和车辆 → 独立检查或业务单 → 核对检查与报价 → 费用责任成套确认 → 派工与回单 → 本轮绩效/交单 → 收款收据 → 取车离场。
- [ ] 同时覆盖先收部分款再维修、检查后客户暂不维修、维修完成但客户稍后取车三个分支；独立状态分开显示。
- [ ] 按第 4 节职责拆两个大详情组件，沿用验证过的数据与服务；实现稿和正式版本清楚区分。
- [ ] AI 从真实格式的测试回单提取名称、描述、类别、整数数量、价格依据与中英文本；明确报价和模糊报价分别验收。
- [ ] 处理多端刷新、页面退出、未知提交结果、重复点击与并发修改；打印成套和补打旧版本。

**交付：** 可在隔离正式后端跑通的完整业务，不是前端演示。

**通过条件：** 员工不依赖开发者逐步提示完成流程；人工复算金额/绩效与页面和单据一致；刷新、重登、重启后结果一致；三端真实操作证据齐全。

### 阶段 4：补齐首发全范围和异常闭环（建议 10–15 个工作日）

- [ ] 客户变更、公司联系人、车辆归属历史、同车多单、撤回改派、返修与跨月绩效调整。
- [ ] 部分收款、多次收款、退款、更正、旧收据补打、未结余额与授权处理；不把退款自动变成绩效扣减。
- [ ] 停车起算/暂停/免费期/免除/历史费率及独立应收收退款；采用已定版经营规则。
- [ ] 报告/轮次/单据无效时有可执行的纠正与解除依赖路线，明确原始审计和发送副本仍存在。
- [ ] 员工账号启停、维修工手机权限、班组变更和合并、基准工资与绩效参数生效版本、历史月复算。
- [ ] 接已有短信接口：先鉴权再发送，记录请求与供应商回执，区分请求发起/供应商接受/送达/客户回复；未知结果先核对，不盲目重复发。
- [ ] 内部留言/@提醒/待办与业务对象连接；客户说“下周再决定”进入待跟进而不是自动算闭环。
- [ ] 管理后台配置门店/Logo/单据、账户权限、AI 模型与预算/缓存、短信/邮件、附件和备份状态。
- [ ] 工作台/报表来源统一，可下钻；AI 缓存按用户权限、对象版本、模型/提示版本隔离并失效，不能串数据。

**交付：** 首发范围全部可用，每个业务异常有实际可走的处理路径。

**通过条件：** 第 8 节中本阶段涉及的业务场景通过；涉及业务含义的缺口已经解决，不以“稍后再试”或“联系开发者改数据库”算完成。完整迁移场景 A17 在阶段 5 执行；全部 A01–A20 的汇总放行在阶段 6，不能提前宣布全系统验收完成。

### 阶段 5：Lark 迁移工程与演练（范围盘点可从阶段 1 并行；全量演练建议 5–10 个工作日）

按第 6 节流程实施。迁移映射必须等阶段 1 规则和目标数据结构明确，不能边导正式数据边改模型。

**负责人：** 工程负责人实现与校验，管理员裁决旧身份/字段，前台核对实际样本。

**交付：** 来源盘点、字段/身份映射、可重复运行导入器、试导和全量演练报告、金额及附件对账、最后增量方案。

**通过条件：** 所有纳入迁移的记录均有导入/明确排除/隔离待处理结果；金额无未解释差异，身份无自动猜配，重复导入不重复计款；评论/历史取得范围有实证和用户接受的边界。切换范围内在场车辆、未结余额、继续维修的异常记录必须已有员工可执行的接续方案，不能只列“已隔离”就放行；不影响当前操作的历史未知资料可明确保留待处理。

### 阶段 6：独立发布审查与员工 UAT（建议 5–10 个工作日）

- [ ] 人类程序员审代码结构、权限、密钥、事务幂等、迁移、依赖与部署；把关键问题逐个关闭。
- [ ] 前台、维修工、管理员和老板视角分别在隔离正式环境执行第 8 节；记录测试账号、版本、输入、预期、实际、证据和复核人。
- [ ] 使用真实手机/iPad，不以调视口替代相机、键盘遮挡、触摸、上传与打印的最终验收。
- [ ] 按当前实际数据规模和预计 2 倍量级压测查询/上传/后台任务，先记录测量环境和并发假设，再定上线容量。
- [ ] 运行账户停用、越权、并发保存、网络超时、备份损坏/缺件、数据库恢复、应用回退演练。
- [ ] 完成员工简明操作手册和管理员应急手册；培训用真场景，不讲代码。

**通过条件：** 第 9 节硬门槛全部满足，未解决低风险问题有负责人和处理日期；用户认可视觉与日常路径；程序员给出可发布结论。

### 阶段 7：受控试运行、正式切换与稳定期（建议 1–2 周试运行，随后至少 2 周重点保障并覆盖首个真实月度绩效复核）

执行第 7 节切换清单。试运行不是提前忽略安全门槛上线；试运行前，真实收款/隐私/备份所需门槛同样必须通过。

**交付：** 一次切换演练、唯一录入规则、最终迁移对账、正式上线记录、值班表、问题台账。

**试点退出条件：** 指定业务稳定运行，按日收退款、余额、在场车辆及附件逐项核对；没有未关闭的高风险问题；月度绩效的隔离跨月算例已经通过。1–2 周试运行不等于已经经历真实月结。

**正式切换条件：** 阶段 6 门槛、试点退出条件、最终迁移对账和当日冒烟全部通过，用户和工程负责人共同放行；若重大规则或金额差异仍未解决，顺延切换。

**稳定期结束条件：** 正式切换后至少 2 周，且首个真实结算/月度绩效周期完成独立复核、没有未解释差异；维护交接通过。若切换日期离月结较远，保障期延长到该复核完成，不为了符合两周期限提前结束。

## 6. Lark 迁移不能简化成“导入 Excel”

1. **核实可取得的数据。** 表、记录 ID、字段类型、关联、附件、评论、历史版本、原作者和原时间分别试导；API/导出权限与限制目前没有被本计划确认。不可取得的内容列出来，不编造。
2. **原始数据归档。** 保存经授权取得的源数据、提取时间、来源 ID 和校验值，作为迁移依据；先做小样本，不为试验反复全量复制附件。
3. **字段分类。** 业务事实进入目标结构；重复列合并；统计列由正式事实重新计算；不再需要的列可仅归档或不迁。不是 Lark 每一列都新建数据库字段。
4. **拆分对象。** 旧记录里挤在一起的客户、车辆、检查和业务单拆成关联对象；分不清的暂存待裁决，不能自动把检查变成已确认收费。
5. **身份映射。** 原作者、员工、登录账号分开；管理员可把旧作者映射到员工/账号，原显示名和时间保持。未知作者不建可登录假账号；班组合并保留旧名、旧归属和有效时间，空值不猜填。
6. **稳定导入身份。** 每条来源记录有来源 ID、导入批次、目标 ID 和结果；重跑只处理可识别的变更，不重复生成收费/收退款/通知。导入执行人/时间与原业务作者/时间分开保存。
7. **财务历史分层。** 有逐笔事实才能迁为逐笔收付款；只有汇总余额时形成明确标识的迁移期初/历史摘要方案，先由业务和工程审核，不能伪造 Receipt 或收款时间凑平账。期初不得计作切换日新增收入、收款或绩效；摘要与逐笔事实按明确截止时间互斥，后续收退款只计一次。对账按币种/最小单位、原始时区与门店业务日期分别核对，不能只有总余额相同就通过。
8. **附件。** 迁入私有存储，核对数量/字节/哈希/对象关联；失效链接、缺件和重复附件有清单与处理结果。备份恢复同时覆盖库和附件。
9. **试导 → 全量隔离演练 → 对账 → 正式增量/最终导入。** 每次输出记录数、关系完整性、金额、分月绩效、在场/停车、作者时间保留率、附件完整性和异常清单。

迁移自动化可以让 AI 建议字段映射、识别重复和翻译；最终身份合并、金额归属、删除来源、覆盖已有资料不能由 AI 自行决定。

## 7. 试运行、切换与回退怎么做

### 切换前

- [ ] 指定一个工程发布负责人、一个前台业务负责人、一个备份替班联系人；工程负责人管理域名/证书/账号恢复与监控，不让用户每天叫 AI 启动。
- [ ] 选择覆盖单店代表性业务的试运行批次。每张业务单必须明确唯一录入系统；试运行期间不让同一笔款在 Lark 和新系统同时当正式记录。
- [ ] 未纳入试运行的业务仍在 Lark；试运行按整车当前业务簇划分，同车有效业务单、停车和关联应收的处理权威不能被拆散。月度绩效若跨系统取数，指定唯一汇总口径和对账负责人，不能两边都声称算出了“完整本月”。
- [ ] 明确正式停写时间、最后增量或重新导出方式、预计停机窗口和失败恢复窗口，提前通知员工。
- [ ] 保留旧系统只读查阅方案；“只读”是否能由 Lark 权限配置落实需实际核验。
- [ ] 演练用户登录、重置密码、查历史、附件、成套打印、收款幂等、监控告警和恢复。

### 切换当天

1. 冻结本次应用、导入器和数据库迁移版本，记录版本标识及兼容的回退版本。旧系统按批准范围停写，记录截止时间；备份必要数据和配置。
2. 在员工写入关闭的状态下执行已演练的目标库迁移，确认实际结构版本与导入器一致；失败停止，不向不匹配的数据库导入。
3. 导入最后增量并对账，在场车辆、未结订单、应收余额、当月绩效与附件优先人工复核。
4. 发布冻结版本，执行正式冒烟；核对通知和后台任务队列，历史导入不触发外发、重复记款或重生成旧收据。失败不开放员工写入。
5. 业务与工程两位负责人签字放行，按清单启用所需任务并发放账号和操作入口，新系统成为批准范围的唯一写入系统。
6. 前台记录首批业务编号并复核，值班人员检查错误、队列、容量和备份状态。

### 出现问题如何回退

- 页面问题：关闭受影响功能、回退经过验证且兼容当前数据库的应用版本；其他业务是否继续由事件负责人判断。
- 数据写入风险：立即暂停相关写入，保存日志、回执和现场数据；按已演练的数据库/附件一致恢复方案执行。
- 切换后已有新业务：先导出并核对新增收退款、交单、绩效、附件等事实，确定接续方法；绝不能直接还原旧备份把新业务抹掉。
- 恢复 Lark 录入时，明确重新开放时间和业务编号对应，逐笔接续，不让两个系统同时变成账目权威。
- 恢复后核对金额、身份、附件和通知；修复/回退本身记录操作人、时间、原因与影响范围。

### 稳定期后的维护交接

以下是维护方案的建议基线，由阶段 2 的工程负责人结合服务预算定版；正式切换前必须填入具体姓名、渠道、时间和费用，不能只有“有人负责”。

- **联系与替班：** 记录主要维护人和替班人、营业时段、非营业时段安排、故障联系渠道及约定响应时间。无法登录、金额异常、越权或数据丢失风险有紧急升级渠道；通知发出不等于已有人接单。
- **每日自动检查：** 可用性、数据库/附件备份结果、容量、失败任务和外发异常；失败通知维护人，未确认处理则升级给替班人。
- **定期恢复演练：** 建议每月在隔离环境抽样恢复库和附件，重大迁移前后再做专项验证；建议每季度演练一次完整恢复。实际频率和可恢复点/恢复时长须由成本及实测确定。
- **更新与续期：** 每月检查依赖和系统更新，高风险安全问题按影响加急；更新先在预发布验证。域名、证书、云服务和接口账户的续期与付款分别指定负责人，设置到期提醒。
- **容量与费用：** 每月复核附件、数据库、日志、AI 和短信增长，按批准保留期清理；生产备份与可再生成的构建缓存分别管理，清理不依靠临时聊天决定。
- **交接材料：** 可复现源码版本、部署/恢复手册、配置键清单、权限与账户所有权、监控入口、已知问题、供应商与账单责任。密钥通过安全渠道交接，不写进文档或代码仓库。
- **退出验收：** 接手程序员能独立部署、定位一例失败、恢复样本、处理账号恢复；维护与业务负责人签收，并落实持续维护预算。未通过时不能声称“交付结束，后面自行维护”。

## 8. 上线必须执行的业务验收场景

每个场景记录版本、角色、设备、数据来源、步骤、预期/实际、API/数据库核对和截图/PDF证据。写入测试只用隔离环境；正式试运行的真实动作由授权员工执行。

| ID | 场景 | 必须证明 |
| --- | --- | --- |
| A01 | 建客户/车辆、公司联系人、缺资料、已填身份重复 | 对象独立，普通待补可继续，身份冲突有明确定位/解决路线，原档不被错误合并 |
| A02 | 客户变更/车辆转属 | 新业务用当前责任方，旧 BO 与单据保持原责任快照 |
| A03 | 独立检查、来源 BO 检查、多份报告 | 双向可查，不自动变更 BO 收费/状态，草稿版本可追溯 |
| A04 | AI 明确报价/模糊报价/混合中英/多数量 | 不猜价格和类别；名称描述分开，量价小计可核对，人工优先，原回单可见 |

## 9. 放行标准与服务目标

### 硬性上线门槛

- [ ] 独立程序员审查通过，关键问题全部关闭；清楚列出未解决问题，不以提交测试数量代替结论。
- [ ] A01–A20 的首发适用路径全部有执行结果；例外只能由业务与工程明确批准、说明替代路径和限制，不能暗自缩小范围。
- [ ] 无越权、数据丢失、重复财务写入、金额/绩效无解释差异、不可恢复或核心操作死路。
- [ ] 用户认可关键界面的美观和易用；前台/维修工完成真实设备操作；单据生成、两联、语言、缩放和系统打印均验收。
- [ ] 迁移金额精确对账，身份冲突已裁决或明确隔离；当前在场、未结和继续维修记录有可执行接续路线。全部选定来源记录和附件有去向/异常说明，评论历史可取得边界明确；期初/摘要不重复计入当期收入、收款或绩效。
- [ ] 云环境 HTTPS、正式认证、私有附件、监控、密钥管理、可恢复备份及版本回退均已实际验证。
- [ ] 有维护负责人、故障联系方法、员工手册与稳定期安排；上线不依赖用户电脑保持开机或当前聊天持续在线。

普通客户材料待补不等于发布失败，更不能因为这里有严格技术发布门槛而给每笔业务增加一层审批。

### 建议服务目标（阶段 2 定版，尚未实测承诺）

- 常用列表/查找/详情在代表性门店网络与数据量下，95% 请求主要内容可用时间不高于 2 秒；长后台任务有进度/状态，不堵普通业务操作。
- 手机关键动作触控区至少 44 CSS px；1600×900、常见 iPad、约 390px 手机及放大字体下关键动作/金额不裁切；长表格/文档的横滚限制在对应区域。
- 故障恢复建议目标：业务数据库可恢复点间隔不超过 15 分钟，关键系统 4 小时内恢复；附件与库的一致性单独实测。只有备份频率、异地副本、存储版本和恢复演练证明达到后才承诺。
- 监控至少包含不可用、错误率、磁盘/对象存储容量、备份失败、后台任务积压和短信异常；触发后有责任人和处置步骤。
- 备份保留期、日志保留期、每月基础费用、附件增长和 AI/短信预算在真实盘点后定版，达到阈值告警；不以无限副本和无限日志换取表面安心。

## 10. 排期和费用怎么控制

上述阶段有依赖也能部分并行：阶段 0 后，交互设计与来源盘点并行；云预发布底座与核心闭环分工推进；全量迁移演练等待目标模型稳定；发布审查和培训不能省略。

在“一名资深全栈持续负责、Codex 协作、有人独立审查、员工能够参加验收”的假设下，先预留 **约 10–14 周到正式切换的计划窗口**，稳定期另计，且持续到首个真实月度绩效复核完成。这是资源规划估计，不是按当前源码大小推算出的承诺。阶段 0 结束后用真实风险、Lark 可导出范围和人员投入重新排期；若要重写后端关键模块或来源历史拿不到，必须明确调整。

每周只看四件事：已交付可操作的结果、对应通过证据、尚存问题、下周明确交付。不要再以“改了多少文件”“跑了多少测试”当进度。

预算分开列：工程/独立审查、云运行与数据库、附件与流量、异地备份、域名、短信、AI、维护。采购前给配置、月费、增长假设和上限；不直接花钱开服务。本轮仅维护本计划文档，不新建运行副本或缓存。

## 11. 人员分工与用户需要投入的事情

| 角色 | 负责 | 不把什么推给用户 |
| --- | --- | --- |
| 工程负责人 | 架构、任务拆分、代码、发布、恢复、容量与维护责任 | 服务器日常启动、查日志、改数据库、理解代码 |
| Codex | 按批准任务实现、补测试、整理证据/规则、协助审查和文档 | 不能自行批准自己的上线结果或替代真实员工验收 |
| 独立程序员 | 阶段 0 审查、关键变更评审、发布风险结论 | 不等全部完成才第一次看巨大差异 |
| 用户/业务负责人 | 集中确认经营分歧、评价交互和单据、迁移范围、最终放行 | 不必选择框架、逐项设计 API 或查技术故障 |
| 前台/维修工代表 | 按日常任务验收、指出操作不顺、参加培训 | 不用替开发者遍历所有测试细节 |

用户近期只需要安排一位负责审查/交付的程序员，并在阶段 1 看关键原型和集中规则表；若人员未到位，仍可完成源码盘点和业务原型，但不虚报“已独立审查”。技术工作不以不断追问用户作为默认推进方式。
