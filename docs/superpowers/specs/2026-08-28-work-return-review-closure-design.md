# Business Order 回单与审核闭环设计

状态：用户已于 2026-08-28 确认

## 目标

补齐维修工接车、电子回单、纸质回单、前台审核、退回修改和正式交单之间的真实业务闭环。所有事实写入正式 PostgreSQL，刷新、重登和重启后保持一致。

## 已确认流程

### 接车

- 被派班组维修工以“登记接车”一次提交接车里程和里程照片。
- 里程和照片均为必填；提交成功同时形成接单、里程和照片事实，维修轮次进入维修中。
- 前台保留纸质接单代录能力，但必须选择实际维修工。

### 电子回单

- 维修工提交本轮实际完成项目、未完成或异常说明、工作总结和相关照片或附件。
- 系统自动带入接车里程、里程照片、维修班组、维修工、提交时间和关联检查结果。
- 每次提交形成新的不可覆盖回单版本，并进入回单待审核。

### 纸质回单

- 前台在维修中状态选择“收到纸质回单”。
- 前台选择实际维修工，拍摄或上传纸质单，核对完成项目、录入必要说明和本轮绩效值。
- “确认并正式交单”在同一事务中形成纸质回单提交、现场核对通过和正式交单事实。

### 审核与退回

- 业务工作台提供正式“回单待审核”队列；Business Order 详情同时提供“查看并审核”入口。
- 审核内容包括派工与收费项目、实际完成情况、接车里程和照片、检查结果、维修照片、异常说明、提交人、班组和时间。
- 前台和超级管理员可以审核；维修工不能审核自己的回单。
- 退回原因必填。退回后回到原班组和原维修工的维修中任务；重新提交形成新版本，旧回单和退回原因保留。
- 审核通过必须绑定最新回单。旧回单曾经通过不能让新的未审核回单进入正式交单。
- 审核浮窗同时确认本轮绩效值；“审核通过并正式交单”在同一事务中写入审核和正式交单事实，任一校验失败则两项都不写入。

## 界面规则

- “推进下一步”改为准确的“提交维修回单”。
- “最新回单尚未审核通过”改成可操作的审核卡或提示，提供查看回单和立即审核。
- 审核、退回、接车和纸质回单均使用浮窗，避免详情页右栏继续堆叠表单。
- 付款历史默认收起，条目使用紧凑字号和不易断行的编号与金额布局。
- 所有新增界面提供完整中文和英文，且使用现有平衡亮色/暗色语义主题。

## 数据与权限

- 回单来源明确区分电子回单和纸质回单。
- 回单保存收费项目完成结果的提交时快照、总结、异常说明、实际维修工和附件关联。
- 接车照片和回单附件继续使用受保护的正式文件存储；浏览器只取得鉴权 URL。
- 写入入口服务端重新校验会话、角色、班组归属、当前状态、最新版本和附件归属。

## 验收

- 电子路径：维修工登记里程与照片、提交回单、前台查看、退回、维修工重提、前台审核并正式交单。
- 纸质路径：前台上传纸质单、确认实际维修工与绩效值并正式交单。
- 状态一致：最新回单审核与正式交单原子完成；操作成功后维修轮次直接进入已正式交单。
- 工作台和 Business Order 详情看到同一正式待审核事实。
- 中文、英文、亮色、暗色和 430px 移动页面可操作，无横向溢出和相关控制台错误。
