# Whole Hearted 单应用合并设计

状态：历史设计记录；当前实施以 `2026-08-27-3210-canonical-single-app-design.md` 为准

日期：2026-08-27

时区：America/Jamaica

## 1. 决策摘要

Whole Hearted 正式系统最终只保留一个可运行应用：仓库根目录的 Next.js 16 全栈应用。它同时提供用户已确认的 PC 界面、服务端认证与权限、正式业务 API、PostgreSQL 数据访问、附件和打印能力。

当前 `apps/web` 只作为 3210 PC 界面的视觉与交互迁移来源，不成为生产运行时。迁移完成后：

- 用户只访问一个系统地址，本地开发入口固定为 `http://127.0.0.1:3210`；
- 只启动一个 Next.js 进程；
- 正式运行、测试和生产构建只使用一套 Next.js、React、pnpm 锁文件、环境变量、测试入口和构建产物；
- PC 页面与正式业务模块在同一应用内协作，不再经过 3210 到 3211 的 HTTP 代理；
- PostgreSQL 是客户、车辆、Business Order、金额、权限、审计和业务状态的唯一事实来源；
- 当前 3210 界面的外观、菜单、打印样式和操作方式是冻结的视觉与交互基线。

本设计只处理应用合并和数据边界收束，不重新设计界面、不擅自改变业务规则、不把 Mock 数据迁入 PostgreSQL，也不直接授权生产上线。未冻结的经营规则继续按独立业务规格确认。

## 2. 选择依据

### 2.1 采用：根 Next.js 16 应用承接 PC 界面

根应用已经包含正式 PostgreSQL、数据库迁移、会话、权限、审计和主要业务领域服务。迁移 PC 界面时，这些正式边界保持不动，只将经过审计的设计 token、品牌资产、纯展示组件、交互容器和页面路由迁入根应用。

该方案避免移动真实数据库运行目录、会话密钥契约、上传目录和事务逻辑，也避免把 `apps/web` 中仍存在的 Mock、localStorage 身份和兼容请求层直接带入正式运行时。

### 2.2 不采用：让 `apps/web` 吞入正式服务

`apps/web` 当前使用 Next.js 14、React 18，仍包含 Mock 回落、localStorage 业务状态、旧角色映射、双重认证桥接和独立锁文件。将数据库、认证和全部正式模块反向迁入它，需要同时改动框架版本、服务端边界、运行目录和部署结构，风险高于迁移界面。

### 2.3 不采用：一个网址包装两个 Next.js 应用

反向代理、多 zone 或自定义服务器只能隐藏两个端口，不能消除两个构建、两个运行时和两套故障边界，不满足“一个应用”的目标。

## 3. 最终应用结构

### 3.1 运行边界

最终运行链路为：

```text
浏览器
  -> 单一 Next.js 16 应用（3210）
       -> PC 页面与打印页面
       -> 服务端会话与权限
       -> 同应用 Route Handler / Server Action
       -> 领域服务与数据库事务
       -> PostgreSQL 与持久附件目录
```

不存在第二个 Next.js 服务，也不存在应用内部通过 HTTP 调用自身或本机另一个端口的路径。

### 3.2 代码边界

- `src/app/**`：唯一 App Router。提供 PC 页面、打印页面、登录、注销和 `/api/*` Route Handler。
- `src/components/**`：从 3210 基线迁入并适配后的展示组件与交互组件。
- `src/modules/**`：正式领域服务，继续负责认证、权限、客户车辆、Business Order、维修轮次、Inspection Report、收付款、文档、绩效、停车、收入和审计。
- `src/db/**` 与 `drizzle/**`：唯一正式 schema、迁移和数据库访问层。
- `public/**`：经过归属审计的品牌、字体、打印和界面资产。
- `apps/web/**`：迁移期间保持隔离和只读；不进入正式 workspace、构建、CI 或部署物。视觉迁移全部验收后复制到外置卷上的可恢复参考档案；仓库内原件只有在另行形成精确清单并获得用户删除授权后才移除。

### 3.3 页面与 URL

用户已确认的 3210 菜单和操作路径作为主路径，包括 `/`、`/orders/business`、`/orders/inspections`、`/customers`、`/vehicles`、`/payments`、`/parking`、`/performance`、`/revenue`、`/workbench` 和打印路径。

根应用现有的重复旧路径在对应 PC 页面完成验收前继续保留；完成验收后改为服务器端重定向到主路径，不长期维护两套同义页面。账号管理和审计等根应用独有正式能力迁入 3210 的设置导航后，旧入口再重定向。

### 3.4 认证与权限

- 保留根应用数据库会话、`wh_session` HttpOnly Cookie、会话散列和服务端权限校验。
- 受保护布局在服务端读取真实会话；未登录、失效或被撤销会话直接进入登录流程。
- PC AppShell、侧边栏和按钮只接收服务端验证后的账号与权限 props。
- 浏览器 localStorage 不再保存或决定身份、角色、权限和业务操作资格。
- 服务端每个读取和写入入口继续独立校验权限，隐藏按钮不能代替服务端授权。

### 3.5 数据访问

- PC 页面直接使用同应用 `/api/*` 或明确的服务端读取接口。
- 现有 `/api/formal/*` 代理在所有消费者切换后删除。
- 删除 `FORMAL_BACKEND_ORIGIN`、`NEXT_PUBLIC_USE_MOCK`、`NEXT_PUBLIC_FORMAL_AUTH` 和 `NEXT_PUBLIC_FORMAL_CUSTOMER_VEHICLE` 等双应用或回落开关。
- 正式页面消费正式 DTO，不长期把正式 DTO 转换回 Mock 对象模型。
- localStorage 只允许主题、语言和侧栏折叠等非权威界面偏好。
- 未完成正式数据能力的菜单保留用户已确认的名称和位置，但页面必须明确显示“待接入正式数据”，不得展示或写入伪造业务数据。

## 4. 迁移分解

本次架构合并拆成六个可独立验收的项目。每个项目有自己的实施计划、失败测试、代码审查和验收证据；任何一项失败都不会通过扩大改动范围来掩盖。

### M0：保护当前可用基线

1. 展开当前全部 tracked、ignored 和 untracked 文件，建立逐文件归属 manifest。
2. 区分正式源码、PC 视觉来源、测试、数据库迁移、运行数据、附件、密钥风险、可再生成缓存和垃圾候选。
3. 在外置卷建立新的单应用迁移快照，保存源码 manifest、Git 状态、数据库迁移编号、UI 参考版本和恢复说明。
4. 当前有效正式源码、迁移、测试和规格按可审查批次进入 Git；不把密钥、数据库物理目录、上传内容或可再生成缓存提交到 Git。
5. 在基线可恢复前不移动、覆盖或批量删除 `apps/web` 与根应用文件。

完成门槛：存在可恢复快照、明确 Git SHA、完整迁移链清单、PC 视觉来源清单，且基线测试结果可重复。

### M1：单应用兼容性探针

1. 在根应用引入经过审核的设计 token、Tailwind/PostCSS 配置、品牌资产和最小 AppShell。
2. 迁移一个只读页面：经营概览。
3. 迁移一个写入页面：Business Order 详情及一项正式写操作。
4. 页面直接读取同应用正式 API，使用根服务端会话，不依赖 `/api/formal`、Mock 或业务 localStorage。
5. 验证 Next.js 16、React 19、Tailwind、动态路由、打印、字体、图片和 Playwright 的兼容模式。

完成门槛：两个探针页面在单一根应用中完成登录、读取、写入、刷新、重登和服务重启验证；视觉和交互与 3210 基线一致；3211 不参与探针运行。

### M2：统一视觉壳、登录和导航

1. 迁移完整 AppShell、侧边栏、顶部栏、主题、语言和响应式布局。
2. 将正式账号、角色、委派权限和只读状态作为服务端 props 注入界面。
3. 迁移登录、注销、无权限、维修工 PC 不可用和设置导航。
4. 删除身份切换器、Mock session 和 localStorage 权限判断。
5. 冻结菜单顺序、名称、图标、展开状态和当前页面高亮。

完成门槛：超级管理员、前台、老板只读、维修工四种角色的登录、注销、菜单、只读和越权行为通过；刷新或换浏览器不会改变角色事实。

### M3：按业务域逐页迁移

迁移顺序固定为：

1. 经营概览、收入；
2. 客户、公司、车辆、字典、员工；
3. Business Order、维修轮次、Inspection Report；
4. 收款、退款、Receipt、业务文档和正式打印；
5. 停车、绩效、审计和设置；
6. 业务工作台；
7. 采购、培训、任务等尚未进入正式业务范围的入口。

每个页面必须拆分为：可复用纯展示组件、正式数据容器、服务端权限边界、正式测试和视觉验收。Mock 数据容器、演示 seed、旧身份映射和客户端业务存储不迁入。

业务工作台只有在根正式服务能够提供可靠事实后才接入；在此之前保留菜单和真实的待接入状态。采购、培训、任务等入口同样不回落 Mock，也不在本架构项目中擅自补造业务规则。

完成门槛：该页面使用正式 DTO、真实权限和 PostgreSQL 数据；刷新、重登、换浏览器和重启后结果一致；不存在生产 `mock-*` import 或业务 localStorage；视觉、操作、打印和直接 API 越权测试通过。

### M4：测试、依赖和构建并轨

1. 将仍验证正式行为的 PC 单元测试和 E2E 迁入根测试体系。
2. 移除只验证 Mock/localStorage 行为且没有正式合同价值的测试；删除前先登记归属和替代测试。
3. 统一 Node、pnpm、Next.js、React、TypeScript、Playwright、Vitest、ESLint、Tailwind、PDF和图表依赖。
4. 正式运行、CI 和生产构建只读取根 `pnpm-lock.yaml`、`next.config.ts`、TypeScript、ESLint、Vitest 和 Playwright 配置；参考档案中的旧配置不参与解析。
5. 建立单一验证命令，依次执行静态检查、类型检查、单元/集成测试、迁移重放、正式 E2E 和生产构建。

完成门槛：干净 checkout 使用冻结锁文件完成一次安装和完整验证；不存在必须单独进入 `apps/web` 才能运行的测试或构建。

### M5：单应用切换

1. 根应用开发和生产端口切换为 3210，`APP_ORIGIN` 同步更新。
2. 删除 30 条 `/api/formal/*` 代理、`FORMAL_BACKEND_ORIGIN`、`dev:web` 和 `build:web`。
3. 保留 `/api/health/live`、`/api/health/ready` 并增加可追溯版本信息。
4. 在第二个 Next.js 服务完全停止的情况下执行全部页面、API、附件、打印和正式业务验收。
5. 将 `apps/web` 当前视觉来源连同 manifest 和哈希复制到外置卷参考档案；正式工作树不再依赖它，但仓库内原件不在本阶段删除。

完成门槛：系统只有一个 Next.js 进程和一个公开监听端口；停止 3211 后功能无变化；生产构建物不包含 Next.js 14、Mock、双应用代理、客户端密钥或 `apps/web` 运行依赖。

## 5. 数据保护与恢复

### 5.1 数据库

- 架构合并本身不重新生成或重排既有 Drizzle 迁移，不修改迁移历史编号。
- 所有开发、集成和 E2E 使用隔离数据库，不连接当前业务开发库或救援物理快照。
- 每次需要更改 schema 时单独生成向前迁移，并在空库和升级库各重放一次。
- 单应用切换前执行一致的 PostgreSQL 逻辑备份，记录迁移版本、时间、文件大小和 SHA-256。
- 应用不得因数据库不可用而静默初始化新空库或退回 Mock；readiness 必须失败并阻止切换。

### 5.2 附件与打印资产

- 保持 `UPLOAD_ROOT` 为外置卷或部署持久卷上的绝对路径。
- 切换前生成附件 manifest，记录 storage key、大小、类型和 SHA-256，并与数据库备份使用同一截止时间。
- 迁移代码不改写既有附件 key；下载、打印和退款证据路径必须逐项回归。
- 车辆识别和 AI 设置中的密钥不从浏览器提交，也不进入源码、manifest、日志或构建物。

### 5.3 会话与权限

- 保持 Cookie 名、session pepper、数据库会话表和会话失效规则。
- 端口切换不创建第二套账号或权限来源。
- 如果切换要求用户重新登录，必须是明确、一次性的安全动作，不能通过复制 localStorage 身份维持假登录。

### 5.4 源码与回退

- 每个迁移项目从可恢复的 Git 基线开始，使用独立分支或隔离工作区；不得通过清空当前工作树获得“干净状态”。
- 每一阶段只有在验证通过后才成为下一阶段基线。
- 切换失败时回退到上一已验证应用版本；数据库只允许回退到与当前 schema 兼容的版本，不执行破坏性 down migration。
- 删除任何旧文件前先生成精确 allowlist、备份位置和恢复方法；禁止广泛 glob、递归清空或跟随符号链接。

## 6. 错误处理

- 数据库、上传目录或关键环境变量不可用时，系统显示明确不可用状态并让 readiness 失败。
- 正式 API 失败时页面保留用户尚未提交的输入，显示可定位错误，不刷新成空白或伪造数据。
- 不存在“正式请求失败后读取 Mock”的回退路径。
- 权限错误统一返回 401/403；找不到资源返回 404；业务冲突返回稳定的 409/422 领域错误。
- 数据读取不完整时显示“待补”“待验证”或“异常提醒”，不把缺失事实当作零值或成功。
- 迁移中的未接入页面显示真实状态，不执行假写入。

## 7. 验收门槛

### 7.1 单应用门槛

- 只有一个 Next.js 进程、一个公开端口和一个生产构建物。
- 正式安装只读取根 package manager 锁文件，并且只解析一套 Next.js/React 版本。
- 根源码和生产依赖不 import `apps/web`、`mock-*`、Mock session 或业务 localStorage。
- 不存在 `FORMAL_BACKEND_ORIGIN`、`/api/formal/*` 自代理或 3211 运行依赖。

### 7.2 视觉与操作门槛

- 3210 当前界面的菜单、布局、颜色、字体、间距、表格、对话框、操作顺序和反馈保持一致。
- 1440px PC、常见窄屏状态和打印页面逐页截图比较。
- 关键键盘操作、焦点、加载、错误、重复提交和 reduced-motion 行为通过。
- 视觉一致不能以牺牲真实权限、正式数据或服务端安全为代价。

### 7.3 认证与权限门槛

- 超级管理员、前台、老板只读、维修工四个角色完成真实登录、注销、会话撤销和菜单验证。
- 隐藏按钮、直接 URL、直接 API 和重放请求均不能绕过服务端权限。
- 浏览器篡改 localStorage 不改变账号、角色、金额或操作资格。

### 7.4 数据与业务门槛

- 客户、车辆、Business Order、维修轮次、Inspection Report、交单、收款、退款、Receipt、取车/停车、绩效和审计读取同一正式事实。
- 页面刷新、重新登录、换浏览器和单服务重启后数据保持一致。
- 已批准的收付款、交单撤销、Receipt、退款、打印和离场流程完成浏览器全流程验收。
- 金额由测试和人工抽样复算，页面、数据库、Receipt 和经营概览一致。

### 7.5 工程与恢复门槛

- 类型、静态检查、单元、集成、E2E、迁移重放和生产 build 全部通过。
- 完整验证从干净 checkout 和隔离数据库开始，不依赖预先运行的第二个服务。
- 数据库与附件备份能够恢复到独立环境；恢复后登录、读取、下载和打印抽样通过。
- Git SHA、迁移版本、构建版本、验收结果和备份 generation 绑定记录。

## 8. 实施责任与汇报方式

Codex 负责迁移顺序、文件归属、测试选择、数据保护、代码审查、浏览器验收和失败回退。用户只需要确认业务结果、界面是否仍是原来的使用方式，以及任何尚未冻结的真实业务规则。

每一阶段汇报只包含：完成了什么、真实验证结果、仍有什么风险、下一步业务上需要用户确认什么。内部端口、测试框架和迁移命令只有在影响用户决定或排障时才展开。

## 9. 完成定义

只有同时满足以下条件才能宣布合并完成：

1. 根 Next.js 16 是唯一运行应用并使用 3210；
2. 当前 3210 PC 界面和操作方式通过逐页验收；
3. 所有正式页面只使用 PostgreSQL、服务端会话和正式业务模块；
4. 第二个 Next.js 服务、30 条代理、Mock 回落和业务 localStorage 已退出生产路径；
5. 一个安装、一个测试入口、一个构建和一个部署物可从干净环境重复生成；
6. 数据库、附件、权限、金额、打印、重启和恢复门槛全部通过；
7. 未接入正式能力的页面如实标记，不展示或写入伪造业务数据。
