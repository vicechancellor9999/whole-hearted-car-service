# Whole Hearted 正式系统端到端候选验收清单（未批准）

**候选状态：** 未批准；本清单中的规则是候选条款，不是最终权威。\
**验收依据（候选）：** `docs/architecture/FORMAL_SYSTEM_BUSINESS_BASELINE.md`\
**验收范围：** 单店正式系统、PC 管理端、维修工手机端、正式后端、数据库与正式打印快照\
**通过标准（候选）：** 本清单全部适用项目均有实际操作证据并通过；最终验收以用户明确发言、已批准设计和已批准分模块规格为准。

## 1. 验收原则与记录要求

- [ ] 使用隔离的正式结构验收数据库和真实后端服务，不使用仅存在于浏览器内的数据。
- [ ] 分别使用超级管理员、前台、老板和维修工账号完成角色路径。
- [ ] PC 路径使用真实浏览器；维修工路径使用真实手机浏览器或与手机视口和输入方式一致的受控设备。
- [ ] 每个关键步骤记录日期时间、角色、账号、URL、业务编号、输入、页面结果、数据库结果和验收人。
- [ ] 每个关键写入操作都验证页面刷新、退出重登后仍存在。
- [ ] 完成核心闭环后重启应用服务并重新登录，验证客户、车辆、报告、订单、轮次、版本、收付款、打印、取车、绩效和审计保持一致。
- [ ] 对金额、GCT、余额、日报、月报和绩效执行独立手工复算。
- [ ] 页面显示与数据库事实不一致时，本项判定不通过。

## 2. 验收数据准备

- [ ] 创建超级管理员、前台、老板只读和同一维修班组内的维修工甲、维修工乙账号。
- [ ] 创建另一个维修班组及维修工丙，用于撤回改派验收。
- [ ] 准备一个含 TRN 的个人客户、一个无 TRN 的个人客户、一个公司客户和两个公司联系人。
- [ ] 为客户准备至少两辆车，其中一辆车用于同车多 Business Order 验收。
- [ ] 准备工时、配件、其他费用三类收费行，至少一种有效支付方式和一项有效 GCT 配置。
- [ ] 准备车辆照片、检查照片、施工照片和可上传的已签字退款签收单文件。
- [ ] 准备有目标和未设置目标两种经营指标配置。

## 3. 客户、公司与联系人路径

- [ ] 以前台在 PC 端创建含 TRN 的个人客户，保存后显示标准化身份资料。
- [ ] 创建无 TRN 的个人客户，输入带空格、连接符或括号的手机号，保存后显示标准化手机号。
- [ ] 使用同一手机号的另一种书写形式再次创建无 TRN 个人客户，确认后端拒绝且没有新增客户记录。
- [ ] 创建公司客户并留空 TRN，确认可保存。
- [ ] 为公司添加两个联系人，确认公司详情同时列出两个联系人。
- [ ] 编辑其中一个联系人，确认新内容生效且历史和审计保留修改前内容。
- [ ] 使用已存在的标准化 TRN 创建另一客户，确认后端唯一性校验拒绝写入。
- [ ] 刷新、退出重登并重启服务，确认客户、公司、联系人和历史保持一致。
- [ ] 以老板账号打开同一资料，确认可查看且无法新增、编辑或删除。

## 4. 车辆归属、照片与关联路径

- [ ] 将测试车辆关联到个人客户，确认车辆详情显示当前归属。
- [ ] 上传车辆照片，确认显示照片用途、上传人和时间。
- [ ] 变更车辆当前归属到公司客户，确认新 Business Order 默认使用公司作为费用承担主体。
- [ ] 打开变更前创建的 Business Order，确认历史费用承担主体仍使用创建时快照。
- [ ] 在车辆详情确认可汇总查看车辆照片、检查结果、Inspection Report、Business Order、取车和停车历史。
- [ ] 从车辆详情打开关联 Business Order 和 Inspection Report，再返回车辆详情，确认关系可双向追溯。
- [ ] 刷新、退出重登和服务重启后，确认车辆归属、照片及全部关联保持一致。

## 5. Inspection Report 路径

- [ ] 从车辆详情创建第一份 Inspection Report，不选择来源 Business Order，确认保存成功并生成独立编号。
- [ ] 从 Business Order 详情为同一车辆创建第二份 Inspection Report，确认来源 Business Order 自动关联。
- [ ] 再为同一 Business Order 创建第三份 Inspection Report，确认该 Business Order 详情同时列出两份来源报告。
- [ ] 确认三份 Inspection Report 均出现在车辆详情中。
- [ ] 确认创建报告未改变 Business Order 或维修轮次状态，也未自动新增收费行。
- [ ] 更正第二份报告，确认产生新版本或更正记录，原内容仍可查看。
- [ ] 刷新、退出重登和服务重启后，确认报告编号、内容、照片、来源、版本和列表保持一致。

## 6. Business Order 创建与首轮维修路径

- [ ] 以前台为测试车辆创建 Business Order，记录正式唯一编号、费用承担主体和联系人快照。
- [ ] 确认首个维修轮次为 `待派单`。
- [ ] 将维修轮次派给维修工甲、乙所在班组，确认状态变为 `已派单`，并记录派单人和时间。
- [ ] 以维修工甲登录手机端，确认能看到所属班组的有效派单。
- [ ] 以维修工乙登录手机端，确认也能看到同一班组派单。
- [ ] 由维修工乙接单，确认状态变为 `维修中`，接单事实记录维修工乙和时间。
- [ ] 随后由维修工甲尝试接同一轮，确认后端拒绝并且首个接单事实未被覆盖。
- [ ] 维修工乙可填写施工内容、参与人员并上传施工照片，确认已填写内容归属当前维修轮次；留空这些可选内容时不阻断回单或前台推进。
- [ ] 维修工乙提交回单，确认状态变为 `回单待审核`，回单内容和照片在 PC 端可见。
- [ ] 前台退回回单并填写原因，确认原回单和退回历史保留。
- [ ] 维修工乙提交后继回单，确认再次进入 `回单待审核`。
- [ ] 前台审核通过并正式交单，确认当前轮次变为 `已交单`，生成正式交单、收费、备注、班组、人员和绩效快照。

## 7. 派单撤回与改派路径

- [ ] 为另一维修轮次派给第一班组，确认状态为 `已派单`。
- [ ] 撤回派单并填写原因，确认轮次回到 `待派单`，原派单事实仍可查看。
- [ ] 将该轮次改派给维修工丙所在班组，确认形成新的派单事实。
- [ ] 以原班组维修工登录，确认无法接取已撤回的派单。
- [ ] 以维修工丙登录并接单，确认状态变为 `维修中`。
- [ ] 接单后再次执行授权范围内的撤回改派，确认旧派单、接单、撤回原因和新派单全部保留。
- [ ] 检查并发接单与撤回请求，确认后端只接受符合当前版本的一次有效状态变更。

## 8. 收费、分类、折扣、GCT 与版本路径

- [ ] 在 Business Order 中分别创建工时、配件、其他费用收费行。
- [ ] 每行填写项目名称、描述、单位、数量、含税单价和本项折扣，确认含税折后小计准确。
- [ ] 确认收费编辑和汇总界面只提供收费行本项折扣。
- [ ] 确认三类收费分别汇总，全部收费行形成含税应收总额。
- [ ] 按当前有效 GCT 税率手工复算含税应税金额中的 GCT，确认页面、后端和打印快照一致。
- [ ] 保存收费，记录收费版本号；修改一行数量或折扣后再次保存，确认生成新收费版本。
- [ ] 打开旧收费版本，确认旧行、旧金额、旧 GCT、修改人、时间和原因保持不变。
- [ ] 保存第一版 Business Order 备注，再修改并保存，确认备注版本独立递增，收费版本未随之变化。
- [ ] 修改收费版本，确认备注版本未被覆盖或重新编号。
- [ ] 正式交单后修改当前收费与备注，确认已生成的正式交单快照仍引用交单时版本。

## 9. 同月取消交单、再次交单与跨月售后路径

- [ ] 在正式交单所在业务月份取消该次交单，填写原因，确认原交单事实标记为已取消且不可删除。
- [ ] 确认维修轮次回到 `回单待审核`，取消人、取消时间和原因完整记录。
- [ ] 确认被取消交单对应绩效不再计入统计，但原绩效事实和审计仍可查看。
- [ ] 再次审核并正式交单，确认生成新的交单事实和新的绩效事实，旧事实未被覆盖。
- [ ] 使用跨业务月份的受控验收数据模拟售后回厂，在原 Business Order 下新建维修轮次。
- [ ] 确认原月份有效交单和绩效保持不变，新轮次从 `待派单` 开始。
- [ ] 完成新轮次的派单、接单、回单、审核和正式交单，确认绩效计入新交单月份。
- [ ] 分别验证正值、零值或负值的售后绩效事实能够保存计算依据并正确汇总。

## 10. 逐笔收款与 Receipt 路径

- [ ] 对同一 Business Order 登记第一笔收款，确认生成独立不可修改收款记录和一张唯一 Receipt。
- [ ] 登记第二笔不同金额或方式的收款，确认生成第二张不同编号 Receipt。
- [ ] 核对每笔收款的金额、方式、时间、操作人、备注和归属对象。
- [ ] 核对累计收款、累计退款和余额由逐笔事实自动计算。
- [ ] 打开第一张 Receipt 中文版和英文版，确认共用同一编号和同一数据快照。
- [ ] 核对两种语言的客户、车辆、收费、历次收付款、本次收款、方式、收款后余额和生成时间语义一致、金额一致。
- [ ] 修改当前收费和备注后补打第一张 Receipt，确认仍使用原编号、原收费版本、原备注版本和原余额快照。
- [ ] 尝试通过页面和直接接口修改或删除收款、Receipt，确认后端拒绝且数据无变化。

## 11. 退款与中英文退款签收单路径

- [ ] 以前台登记一笔退款，填写关联对象、金额、方式和原因，确认先生成独立退款事实。
- [ ] 确认退款登记没有改写原收款、Receipt、收费版本、正式交单或绩效。
- [ ] 登记成功后生成中文版和英文版退款签收单，确认两种语言共用同一退款编号和同一快照。
- [ ] 核对两种签收单的客户、车辆、退款金额、方式、原因和时间语义一致、金额一致。
- [ ] 打印退款签收单并由客户签字。
- [ ] 上传已签字退款签收单，确认保存上传人、上传时间和附件审计。
- [ ] 补打退款签收单，确认沿用原编号和原快照。
- [ ] 尝试修改或删除退款、替换已归档签字附件，确认后端拒绝。
- [ ] 核对退款后的余额按正式公式变化，日报和月报财务数字同步变化。
- [ ] 核对正式交单绩效和绩效报表不因退款发生变化。

## 12. Business Order 打印路径

- [ ] 生成 Business Order 办公室联，确认保存文档编号、收费版本、备注版本、生成时间、生成人和完整数据快照。
- [ ] 生成维修工联，确认显示车辆、维修轮次、班组、施工项目和施工备注。
- [ ] 确认维修工联不显示客户联系方式、收费、收付款、余额或绩效。
- [ ] 修改客户、车辆、收费、备注和收付款当前数据后补打两份文件，确认历史打印内容不变。
- [ ] 重新生成当前版本打印件，确认获得新文档编号并反映当前数据。
- [ ] 验证 Receipt、退款签收单、办公室联和维修工联的 A4 打印预览无系统导航、按钮、文字重叠、内容截断或异常分页。
- [ ] 以老板账号查看并补打历史打印件，确认可以只读访问且不能生成新的正式打印事实。

## 13. 取车、挂账、多单阻断与停车路径

- [ ] 为同一车辆创建两张 Business Order，其中一张保持未正式交单。
- [ ] 在另一张订单已交单的情况下尝试生成取车通知和取车，确认系统按车辆汇总检查并阻断。
- [ ] 将两张 Business Order 的全部有效维修轮次正式交单，确认可以生成有效取车通知。
- [ ] 保持车辆存在未结余额且没有挂账资格，尝试取车，确认后端阻断。
- [ ] 由有权角色批准有效挂账资格，记录批准人、范围、生效时间和原因。
- [ ] 再次取车，确认生成独立取车事实，未结订单进入挂账催收范围。
- [ ] 追加收款使余额为零，确认派生结清结果更新。
- [ ] 为已取车车辆开启售后新维修轮次，确认原取车通知失效，车辆重新进入在场流程。
- [ ] 按正式停车配置触发停车记录，核对起算时间、费率、金额和关联车辆或 Business Order。
- [ ] 生成新维修轮次后，确认不再按已失效取车通知累计后续停车费。
- [ ] 执行停车费免除，确认记录免除人、时间、金额和原因，并进入敏感操作审计。

## 14. Business Order 最终完成路径

- [ ] 仅完成正式交单但未付清、未取车，确认 Business Order 不显示 `已完成`。
- [ ] 正式交单且已付清但未取车，确认不显示 `已完成`。
- [ ] 正式交单且已取车但通过挂账仍有余额，确认不显示 `已完成`。
- [ ] 当前全部有效维修轮次已正式交单、余额为零且已有有效取车事实，确认显示 `已完成`。
- [ ] 直接接口尝试绕过任一条件写入 `已完成`，确认后端拒绝或根据事实重新计算。

## 15. 日报、月报与经营概览路径

- [ ] 在同一业务日完成收款、退款、正式交单、取车、挂账和停车操作。
- [ ] 打开日报，确认财务汇总只显示一个“今日净收款”，页面不再分别展示“今日收款”和“今日退款”汇总数字。
- [ ] 核对日报退款敏感操作逐笔写明车辆、操作人、原因和金额；核对其他敏感操作也按具体事项显示。
- [ ] 手工复算日报净收款与今日正式交单的工时、配件、其他费用分类金额，确认与报表一致。
- [ ] 打开月报，核对正式交单、净收款、未结余额、客户、车辆、Business Order、维修轮次和绩效指标，并确认敏感操作只显示分类数量。
- [ ] 从日报和月报数字下钻到对应正式业务记录，确认编号和金额一致。
- [ ] 打开经营概览，分别切换今日、本周、本月、本年，确认全部指标来自正式后端且时间边界使用门店业务时区。
- [ ] 新增一笔正式后端收款或正式交单后刷新经营概览，确认当前范围实时反映新事实。
- [ ] 对已设置目标的指标核对目标值、完成值和完成率。
- [ ] 对未设置目标的指标确认明确显示“未设目标”。
- [ ] 退出重登和服务重启后，再次核对经营概览、日报和月报结果不变。

## 16. 历史与审计路径

- [ ] 从客户详情追溯公司、联系人、车辆和历史 Business Order。
- [ ] 从车辆详情追溯照片、Inspection Report、Business Order、取车和停车历史。
- [ ] 从 Business Order 详情追溯全部维修轮次、派单、接单、撤回、回单、交单、取消交单、收费版本、备注版本、收付款、打印和绩效。
- [ ] 核对每项敏感操作的操作者、角色、时间、对象、动作、原因、前后值或关联事实编号和请求来源。
- [ ] 尝试修改或删除审计记录，确认后端或数据库拒绝。
- [ ] 以老板账号确认可只读查看业务历史和允许范围内的审计。
- [ ] 以维修工账号确认只能查看所属班组且与施工职责相关的历史。

## 17. 权限与终端路径

- [ ] 超级管理员在 PC 管理端可执行全部正式管理操作和查看完整审计。
- [ ] 前台在 PC 管理端可执行日常业务操作，敏感操作只在取得有效授权时成功。
- [ ] 老板在 PC 管理端可查看客户、车辆、Business Order、Inspection Report、财务、报表、历史和审计，页面无写入入口。
- [ ] 老板通过直接接口尝试新增、修改、删除、派单、收款、退款、交单、取车或生成新打印件，确认全部被服务端拒绝。
- [ ] 维修工账号在 PC 管理端无法进入管理业务页面。
- [ ] 维修工在手机端只能查看所属班组的有效派单、接单、施工记录和回单操作。
- [ ] 维修工尝试访问其他班组订单、客户联系方式、收费、收付款、余额、退款、经营报表或绩效管理，确认服务端拒绝或不返回数据。
- [ ] 撤销前台敏感授权后刷新页面并重试直接接口，确认授权立即按正式会话规则失效。

## 18. 绩效路径

- [ ] 首次正式交单后，核对绩效事实保存交单时间、业务月份、维修轮次、班组、人员、绩效值和计算依据。
- [ ] 修改当前收费、备注、收付款、挂账、取车和停车后，确认原绩效事实和汇总不变。
- [ ] 登记退款前后记录同一绩效指标，确认退款不改变绩效。
- [ ] 同月取消交单后，确认对应绩效不计入统计；再次交单后只计入新的有效绩效事实。
- [ ] 跨月售后新轮次正式交单后，确认原月绩效不变，新绩效计入新月份。
- [ ] 核对正值、零值和负值绩效在人员、班组、月度及经营概览中的汇总一致。
- [ ] 以老板账号只读查看绩效，以维修工账号查看正式授权范围内的个人施工结果，确认没有管理写入能力。

## 19. 持久化、并发、性能与稳定性路径

- [ ] 建立性能验收数据集：不少于 10,000 个客户、10,000 辆车辆、20,000 张 Business Order 和 100,000 条业务历史或审计记录；保留一张包含不少于 20 个维修轮次、50 份 Inspection Report、100 个附件索引和 500 条历史记录的大型 Business Order。
- [ ] 在两个浏览器窗口同时编辑同一收费版本，先后保存，确认后端阻止后提交者覆盖新版本并给出可恢复提示。
- [ ] 并发执行接单、收款、退款、正式交单和取车请求，确认每项正式事实只产生一次有效结果，金额与状态守恒。
- [ ] 对客户、车辆、Business Order 和 Inspection Report 列表执行常用条件搜索、筛选、排序和分页；连续测量 20 次，后端响应时间第 95 百分位不超过 2 秒，结果正确且页面可持续操作。
- [ ] 打开大型 Business Order 详情；连续测量 20 次，后端首个详情响应时间第 95 百分位不超过 3 秒，分段内容可继续加载且页面操作不被长任务阻塞。
- [ ] 对今日、本周、本月、本年经营概览及月报连续测量 20 次，后端响应时间第 95 百分位不超过 5 秒，且所有数字与同一数据集的逐笔复算一致。
- [ ] 对客户保存、派单、接单、回单、收款、退款登记、正式交单和取车各连续测量 20 次；排除附件传输和浏览器打印对话框等待时间后，后端响应时间第 95 百分位不超过 2 秒。
- [ ] 使用 20 个并发业务会话持续执行读取与写入混合路径 15 分钟，确认服务端请求错误率低于 1%，且收款、退款、Receipt、正式交单和取车均无重复有效事实。
- [ ] 上传项目允许上限内的车辆、检查、施工和签字附件，确认上传、权限下载和列表加载稳定。
- [ ] 关键页面操作期间检查浏览器控制台、服务日志和数据库日志，确认无未处理异常、权限泄露或重复写入。
- [ ] 重启应用服务后复验关键路径；重启数据库后按正式恢复流程复验关键路径，确认编号、事实、版本、快照和审计完整。
